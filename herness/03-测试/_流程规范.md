# 测试流程

> 测试工作流：本项目以**类型门禁 + 手工用例 + 契约核对**为主，暂无自动化测试框架。

---

## 一、现状说明

- ❌ 无 vitest / jest 依赖
- ❌ 无 `test` 脚本
- ⚠️ `tests/*.test.ts`（9 个）为历史遗留，需自备 runner
- ✅ 有 `pnpm lint`（vue-tsc）作为类型门禁

---

## 二、流程概览

```
技术方案完成
  │
  ├─→ 1. 类型自检      → pnpm lint（无新增报错）
  ├─→ 2. 编写测试用例  → 03-测试/测试用例/
  ├─→ 3. 执行验证      → 手工执行 / 自备 runner 跑遗留脚本
  ├─→ 4. 契约核对      → 事件键/DTO/接口 与 docs/source/** 一致
  └─→ 5. 输出报告      → 03-测试/测试报告/
```

---

## 三、测试维度（结合本项目特点）

| 维度 | 检查项 | 方法 |
|------|--------|------|
| 类型正确性 | `strict` 报错、未用变量 | `pnpm lint` |
| 分层合规 | 是否越层、通用层是否混业务 | 对照 `05-共享上下文/设计规范速查.md` 逐条确认 |
| 协议契约 | 事件键/DTO 是否与 `docs/source/**` 一致 | 人工比对 |
| 消息链路 | 订阅是否取消、拦截器是否注册、事件键是否正确 | 手工触发 + 观察 |
| 坐标与空间 | WGS84 顺序、缓冲区、AOI | 用例验证边界 |
| 状态与异常 | 接口失败、断线、空数据、权限 | 手工验证兜底 |
| 回归 | 是否破坏既有功能 | 手工回归受影响页面 |

---

## 四、测试类型与门禁

| 类型 | 何时做 | 门禁 |
|------|--------|------|
| 类型自检 | 每次编码后 | `pnpm lint` 无**新增**报错（基线约 193 个既有问题） |
| 用例编写 | 测试阶段 | 关键路径 + 异常路径覆盖 |
| 手工验证 | 测试阶段 | 记录实际结果 |
| 契约核对 | 涉及消息/接口时 | 与 `docs/source/**` 一致 |
| 回归验证 | 修复 Bug / 改动公共层时 | 受影响路径无退化 |

---

## 五、进入 MR 的门禁

- [ ] `pnpm lint` 无新增报错（已对比改动前后）
- [ ] 测试用例已编写并执行
- [ ] 异常路径已验证
- [ ] 涉及消息/接口时契约已同步
- [ ] 测试报告已产出

---

## 六、引入自动化测试（建议）

若团队决定引入：在技术方案中明确选型（建议 vitest + @vue/test-utils），补充 `package.json` 的 `test` 脚本，并优先覆盖 [单元测试/_index.md](../02-技术设计/前端/单元测试/_index.md) 中列出的纯逻辑模块（无 DOM / 无引擎依赖）。

# 测试接缝规范

> **回答什么问题**：这个测试该测在哪一层边界？哪些内部不该碰？
> **何时读**：写测试用例前、评审「这个用例在测什么」时。
> **契约真相源**：`tests/harness/README.md`（四要素 + GIS 专用契约）；本文件补充「**接缝在哪**」。

## 二、核心规则

> **一、先定接缝，再写测试。**

不是「想到什么测什么」，而是先列出**待测接缝清单并与人工确认**，再动手写用例。

理由：测不完所有东西。事先约定接缝，测试投入才落在**关键路径与复杂逻辑**上，
而不是每个边界情况都写一遍。

每条待测接缝需写一行说明：**能拦住什么 / 会漏掉什么**。

> **二、接口即测试面。**

调用方与测试穿**同一个**接缝。想测穿界面（越过接口摸内部结构），
说明这个模块形状错了——先改模块，不要改测试去迁就。

> **三、一个 adapter = 假想接缝。**

只有一个 adapter 时不要为了「将来可能换实现」去抽象端口。测试替身本身**就是**第二个 adapter。

## 三、本项目接缝表

| 层 | 接缝位置 | 用什么测 | 测试替身 | 落在哪 |
|---|----------|----------|----------|--------|
| 纯计算 | 单个导出函数 | vitest 直接调 | 无 | `tests/unit/**` |
| 坐标转换 | `amapCoordinate.ts` 单一入口 | vitest + 回归用例 | 无（纯函数） | `tests/unit/**` |
| 工具函数 | `src/utils/**` 公开导出 | vitest | 无 | `tests/unit/**` |
| 消息收发 | `useMessageStore().publish/subscribe` | vitest + 拦截器链 | 内存 emitter | `tests/unit/**` |
| HTTP 接口 | `src/apis/**` | vitest | `@alova/mock` | `tests/unit/**` |
| 组件 | 组件的 props / emit | vitest + @vue/test-utils（jsdom） | 无 | `tests/components/**` |
| 引擎控制 | `src/controller/core/generic/**` 对外接口 | vitest | OL 实例替身 / 不替身视用例 | `tests/unit/**` |
| 协议契约 | 事件键 / DTO 与 `docs/source/**` 一致性 | vitest + 人工比对 | 无 | `tests/unit/**` |
| 端到端 | 用户旅程 | playwright | 真浏览器 | `tests/e2e/**` |

## 四、按依赖分类决定测法

接缝能不能替换，取决于依赖属于哪一类（详见 [模块设计速查 §4.3](../05-共享上下文/模块设计速查.md)）。

| 依赖类别 | 测法 | 本项目 |
|----------|------|--------|
| 进程内纯计算 | 直接调用，断言返回值 | `src/utils/**` |
| 可本地替代 | 替身跑在测试里，测**接缝之上** | `@alova/mock` 替网关 |
| 远程但自有 | port + 生产/测试双 adapter | 网关、GeoServer |
| 真外部 | 注入 port，测试给 mock adapter | 高德、Cesium 瓦片 |

**推论**：本项目测**不该**去 mock OpenLayers / Three / Cesium 的内部——
它们属「真外部 / 引擎」，断言**业务可观察结果**（图层是否加上了、坐标是否落对了），
而不是引擎内部状态。

## 五、GIS 专用接缝约束

本项目特有，完整契约见 `tests/harness/README.md`，此处只列接缝视角：

| 接缝 | 约束 |
|------|------|
| 坐标系 | 高德边界**只能**出现在入站/出站转换函数上；业务层统一 WGS84 |
| 消息协议 | 收发唯一出口是 `useMessageStore().publish/subscribe`，测试也应在此处断言 |
| 分层 | `core/generic/**` 零业务、`core/business/**` 禁 import ol/three——接缝测试要能**静态发现**越层 |

## 六、替换而非叠加

当一个浅模块被深化为深模块：

1. 在**深模块的接口**上写新用例
2. **删除**旧浅模块上的单测（它们已成 waste，且会随重构频繁破裂）
3. 不要两边都留着——旧测试会把形状锁死在浅模块上，阻止深化

---

## 七、写测试前的自检

| # | 检查 | 不通过 |
|---|------|--------|
| 1 | 待测接缝清单是否已与人工确认？ | 先确认，别直接写 |
| 2 | 用例断言的是**可观察结果**还是内部状态？ | 内部状态 → 改断言位置 |
| 3 | 实现重构后用例还能过吗？ | 不能 → 测过了界 |
| 4 | mock 的依赖是否真的需要第二个 adapter？ | 不需要 → 去掉抽象 |
| 5 | 旧浅模块的用例是否已删？ | 没删 → 叠加而非替换 |
| 6 | 四要素是否可读出？ | 补齐（见 harness 契约） |

---

## 八、与覆盖率阈值的关系

覆盖率是**结果**不是**目标**：

- 某个模块覆盖率低但**接缝不在测试范围**内 → 正常，不必强拉
- 某个模块在**已确认的接缝**上却覆盖不足 → 信号，需要补用例

分模块阈值配置见 `vitest.config.ts`，白名单策略见 harness 契约。

# 模块设计速查

> **回答什么问题**：这个模块该做成什么样？接口该切在哪？该不该抽象？
> **何时读**：新增/重构模块、拆分文件、评估「这层是不是多余的」时。
> **硬门禁**：写新模块前先按 §三 判断深浅，按 §四 定 seam，再动手。
>
> 事实来源：`src/**` 实测 + 方法论参考 `codebase-design` / `DEEPENING.md`。
> 与代码冲突时以代码为准，并回写本文。

## 二、核心词汇

| 词 | 定义 | 本项目对应 |
|----|------|-----------|
| **模块** | 一组对外提供单一接口的代码 | `src/utils/coordTransform.ts`、`src/controller/core/generic/**` 一个子域 |
| **接口** | 调用方必须知道的全部：类型签名 + 不变量 + 顺序约束 + 错误模式 + 必要配置 + 性能特征。**不只是签名** | `src/controller/core/protocol/**` 的 interface |
| **实现** | 模块内部怎么做到的 | 具体函数体、算法、引擎调用 |
| **深度** | 单位接口能承载的行为量。**深**=小接口+多实现；**浅**=接口复杂度≈实现复杂度 | 见 §三 |
| **seam（接缝）** | 能在不改动该处代码的前提下改变行为的位置。**接口就住在 seam 上** | `src/apis/**` 与 `src/service/**` 之间 |
| **adapter（适配器）** | 满足某 seam 上接口的具体实现。描述**角色**不描述内容 | `alovaInstance`（生产）/ `@alova/mock`（测试） |
| **杠杆** | 调用方每次只需学一个接口，却能用到大量行为 | — |
| **局部性** | 改动、缺陷、知识、验证集中在一处，而非散在多个调用方 | — |

## 三、深度：怎么判断模块设计得好不好

### 3.1 删除测试（最快）

**想象删掉这个模块**：

- 复杂度**消失** → 它是透传（pass-through），是浅模块，考虑合并或删除
- 复杂度**重新散到 N 个调用方** → 它有存在价值，是深模块

### 3.2 深浅对照

```
┌───────────────────────────┐
│      小接口（少方法、简单参） │  ← 调用方要学的全部
├───────────────────────────┤
│                           │
│      多实现（复杂逻辑藏起）   │  ← 调用方看不到
│                           │
└───────────────────────────┘
       深模块（要这个）


┌───────────────────────────┐
│   大接口（多方法、复杂参）   │  ← 调用方要学的全部
├───────────────────────────┤
│      少实现（只是转发）      │
└───────────────────────────┘
       浅模块（避免这个）
```

### 3.3 设计接口时自问

1. 能不能**减少方法数**？
2. 能不能**简化参数**？
3. 能不能**把更多复杂度藏进去**？

### 3.4 本项目现状对照（实测）

| 模块 | 深浅 | 判断依据 |
|------|------|----------|
| `src/utils/coordTransform.ts` | **深** | 单一入口封装 GCJ-02↔WGS84 + 距离/面积，调用方只学 1 个接口，复杂度全藏内部。**638m 事故后加的回归测试守在这里** |
| `src/controller/core/protocol/**` | **深** | interface 把 DTO 契约显式化，是「把 seam 声明出来」的正解 |
| `src/store/index.ts` | **浅**（桶导出） | 21 个 `export *`，调用方要学的接口≈整个 store 集合；任一引用拖进整桶 |
| `src/service/alova*.ts` | 中 | 3 个实例 + 各自职责尚可，但**传输层与业务语义混过界**，已由 `src/apis/**` 收口 |
| `src/Control/**` | **浅**（历史遗留） | 透传 + 双实现，删除测试下复杂度会散回调用方，需与新链合并后再清 |

## 四、seam 纪律

### 4.1 硬规则

> **一个 adapter = 假想 seam。两个 adapter = 真 seam。**

没有第二个 adapter，就不要引入 port/接口——那只是**多一层间接**，不换来可测性。

### 4.2 内部 seam vs 外部 seam

一个深模块可以同时有：
- **外部 seam**：模块对外的接口（公开）
- **内部 seam**：实现内部的私有接缝（不暴露）

**不要因为自己的测试用到了内部结构，就把它暴露到接口上**。

### 4.3 接缝选址：依赖四分类

判断一个依赖能不能被替换，决定 seam 放哪、测法是什么。

| 类别 | 特征 | 可深化？ | 本项目例子 |
|------|------|----------|-----------|
| **1. 进程内** | 纯计算、内存态、无 I/O | **总是可以**：合并模块，直接测新接口 | `src/utils/**` 纯函数、`withAlpha` / `cssVar` |
| **2. 可本地替代** | 有本地替身（内存文件系统、内存 DB） | 替身存在即可；seam 是**内部的**，外部接口不需要 port | `@alova/mock`、`useMessageStore` 内存 emitter |
| **3. 远程但自有** | 自家服务跨网络 | 定义 **port**，生产用传输 adapter，测试用内存 adapter | `ids-dev.ks.telewave.tech` 网关、GeoServer |
| **4. 真外部** | 第三方服务，不可控 | 依赖作为注入的 port，测试给 mock adapter | 高德 API、Cesium 瓦片服务 |

**第 3 类的标准说法**：
> 在接缝处定义 port，生产用 HTTP adapter、测试用内存 adapter，逻辑留在一个深模块里，
> 即使部署上跨了网络边界。

### 4.4 本项目已成立的 seam

| seam 位置 | 生产 adapter | 测试 adapter |
|-----------|------------|------------|
| `src/apis/**` ↔ `src/service/**` | `alovaInstance` | `@alova/mock` |
| `useMessageStore().publish/subscribe` | WS / postMessage | 内存 emitter + 拦截器链 |
| 坐标转换 | `amapCoordinate.ts` 单一入口 | 无需替身（纯函数） |

## 五、测试接缝：接口即测试面

> **调用方与测试穿同一个 seam。**

- 想**测穿界面**（越过接口摸内部）→ 说明这个模块形状错了，不是测试写错了
- 测试断言**可观察的结果**，不断言内部状态
- 测试应在内部重构后**依然通过**；若实现一变测试就要改，说明它测过了界

### 5.1 替换而非叠加

- 旧浅模块上的单测，在深模块接口测试建立后**即成 waste**，应删而非留
- 新测试写在**深模块的接口**上
- **不要在旧浅模块上继续叠测试**——那是给透传层加负担

### 5.2 依赖注入三原则

```typescript
// 好：接受依赖，不创建依赖
function processOrder(order, paymentGateway) {}

// 差：内部 new，测试无从下手
function processOrder(order) {
  const gateway = new StripeGateway();
}
```

1. **接受依赖，不创建依赖**
2. **返回结果，不产生副作用**（`calculateDiscount(cart): Discount` 优于 `applyDiscount(cart): void`）
3. **接口面要小**——方法少 ⇒ 要测的少；参数少 ⇒ 夹具简单

## 五点五、生命周期型模块的还原责任（2026-11-04 新增）

单实例常驻架构（如本项目主图 + 调派共用一个 OLMap）下，**共享资源的释放责任归属谁**，必须在设计时写清。

| 资源类型 | 归属 | 规则 |
|---|---|---|
| 共享设施（manager / nav / port） | 常驻方 | 调派侧只**消费**，不 destroy |
| 变体专属资源（点位图层、图层、交互、监听） | 变体方 | 创建方负责在 `deactivate()` 显式还原 |

**强制项**：

1. `deactivate()` 里的还原逻辑**不能依赖 watch 触发**——watch 已 stop，必须显式调用恢复函数；
2. 每新增一类调派专属资源，**必须同步在 `deactivate()` 补还原**（否则切回主图态永久残留）；
3. 还原顺序：**先释放强占（解除图层/交互占用）→ 再复原集合（按主图态重建图层）**；
4. 注册表按用途分槽位持有，**不同用途互不顶替**：`BusinessMessageRuntime.attachMap` 已按 `kind` 分别持有 attachment（主图 `kind:'map'` / 调派 `kind:'dispatch'`），两者同时存活，业务动作按「调派优先、无调派槽位回落主图」自动选槽。**同槽位**重复 attach 才顶替旧的（旧端口被 `valid()` 守卫成 no-op 且不抛异常，需注意）。

> 落地参考：`src/baseComponent/OpenlayersMap/useDispatchEntangled.ts` 的 `deactivate()` 与
> `src/baseComponent/OpenlayersMap/map.vue` 的 variant watch。

## 六、可测试性自检

写完模块后自查：

| # | 检查 | 不通过怎么办 |
|---|------|-------------|
| 1 | 删除测试：删掉它复杂度会散到调用方吗？ | 会散 → 是深模块，保留；会消失 → 是透传，合并掉 |
| 2 | 接口面是否已是最小？ | 砍方法数、砍参数 |
| 3 | 每个依赖都分类过吗？ | 分类后才知道该 mock 哪个、该注入哪个 |
| 4 | 有 adapter 吗？只有一个吗？ | 只有一个 → 别抽象 |
| 5 | 测试穿的是接口还是内部？ | 穿内部 → 改测试位置，或改模块形状 |
| 6 | 接口里有类型签名以外的东西吗？ | 不变量/错误模式/顺序约束要写进 JSDoc |

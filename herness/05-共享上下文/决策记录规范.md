# 决策记录规范（ADR）

> **回答什么问题**：这个架构决策**为什么**是这样？以后能不能改？
> **何时读**：动某个「不好理解为什么这么写」的模块之前；写技术方案时判断要不要留档。
> **落位**：`herness/05-共享上下文/adr/`

---

## 一、ADR 记什么、不记什么

### 1.1 必须同时满足才写

| # | 条件 | 判据 |
|---|------|------|
| 1 | **难以逆转** | 改主意的成本显著（推翻要动数据格式/对外契约/大范围代码） |
| 2 | **无上下文时令人费解** | 后来人看代码会问「为什么这么写」 |
| 3 | **存在真实权衡** | 有被否掉的替代方案，且当时有理由选现在的 |

**三条缺一不可**：
- 容易逆转 → 直接改就行，不用记
- 不令人费解 → 没人会问，不用记
- 没有替代方案 → 记「我们做了显而易见的事」没有价值

### 1.2 典型该记

- **架构形状**：分层方式、模块划分、依赖方向
- **跨上下文集成模式**：消息通道怎么走、状态唯一来源在哪
- **带锁定效应的技术选型**：OpenLayers / Cesium / Three / alova / Pinia / Vite Rolldown
- **边界与归属决策**：某类数据归谁管、哪个目录是唯一真源

### 1.3 不要记

- 日常 bug 修复、代码格式化
- 纯实现细节（函数怎么拆、变量怎么命名）
- 还没定的方案（那是 `02-技术设计/` 的活）

## 二、模板

**一个 ADR 可以只有一个段落**。价值在于记下「**做了什么决定、为什么**」，不是填满章节。

```markdown
# {决定标题}

{1~3 句：上下文是什么、决定了什么、为什么这么决定。}
```

### 可选段（仅在真有价值时加）

| 段 | 何时加 |
|----|--------|
| **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`） | 决定会被 revisiting（回访、推翻、替代） |
| **Considered Options** | 被否掉的替代方案值得记住（避免后人重复走弯路） |
| **Consequences** | 下游影响不显然（性能、迁移成本、运维要求） |

**大多数 ADR 不需要这三段。**

## 三、编号与落位

- 目录：`herness/05-共享上下文/adr/`
- 命名：`0001-slug.md`、`0002-slug.md`…… 顺序编号
- 新建目录是**惰性的**：第一份 ADR 需要时才建
- 取号：扫目录找最大号 +1

### 为什么放 `herness/05-共享上下文/adr/` 而不是 `docs/adr/`

| 理由 | 说明 |
|------|------|
| **两类事实不同源** | `docs/source/**` 是**业务契约**真相源（给外部系统看）；ADR 是**工程决策**（给团队看） |
| **不污染契约源边界** | ADR 混进 `docs/source/**` 会让「业务契约」目录混入内部工程决策，外部消费方不知该不该读 |
| **受既有门禁管辖** | `herness/**` 有 `_index.md` 体量门禁与交接格式检查，ADR 天然在治理范围内 |
| **与 02-技术设计 分工清晰** | `02-技术设计/**` 记**方案与实施过程**；ADR 记**已定版的结论与理由** |

## 四、与现有机制的关系

| 机制 | 记什么 | 生命周期 |
|------|--------|----------|
| `02-技术设计/**/*-技术方案.md` | 方案、落点、风险、验证、待确认项 | 实施完归档进 `_archive/` |
| **ADR（本文）** | 已定版的决定 + 为什么 | 永久保留 |
| `当前状态摘要.md` 关键决策记录 | 一行式时间线（便于快速回溯） | 持续追加 |
| `09-工作日志/**` | 流水账（谁在何时改了什么） | 写完即弃 |

**不重复**：方案里已有完整理由的，不要再抄一遍进 ADR——ADR 写「结论 + 关键取舍」，细节指向方案路径。

---

## 五、什么时候提 ADR

写技术方案时，如果方案里有「**以后会有人问为什么**」的决定，在方案定版时一并起草 ADR。

提请时说明：
1. 决定是什么（一句话）
2. 满足三条判据中的哪几条
3. 候选位置（下一号）

## 六、示例

```markdown
# 消息收发统一经 useMessageStore

消息收发只允许通过 `useMessageStore().publish/subscribe`，
禁止裸 `new WebSocket()` 与裸 `window.addEventListener('message')` 处理业务。

裸实现曾导致两处订阅各自建连、消息被消费两次的问题。
统一出口后订阅关系集中在 store 一处，
新增消息只需注册拦截器与事件键，不需要在业务侧再关心通道。

**Status**: accepted
```

## 二、`.gitignore` 陷阱（🔴 P0 · 已修复）

| 规则 | 风险 | 正确写法 |
|------|------|---------|
| ~~`scripts`~~ | 裸目录名会忽略**整个** scripts 目录 | 用 `/scripts-temp/` 或精确到文件 |
| ~~`src` 的 md 规则~~ | 会屏蔽工程文档 | 精确路径白名单 |
| `skills*` | 屏蔽 skill 目录 | 若需入库则加 `!skills/` 例外 |
| `tests/__artifacts__/` | ✅ 正确：只忽略测试产物 | 保留 |

**新增 `.gitignore` 规则后的自检**：

```bash
git check-ignore -v <新文件>     # 有输出 = 被忽略了，需要修正规则
git status --short                # 新资产必须出现在列表里
```

## 三、分支模型（🟡 P1 · 团队约定）

| 分支 | 用途 | 规则 |
|------|------|------|
| `main` | 生产分支 | 只接受合并，**不直接提交** |
| `dev` | 集成分支 | 功能合并后跑一次全量验证 |
| `dev-<姓名>` | 个人开发分支 | 从 `dev` 切出；**命名统一 `dev-xx`，禁止 `dev-yf-2024` 等日期后缀** |

**提交前先同步**：

```bash
git fetch origin
git rebase origin/dev      # 或 merge，看团队约定
```

> 历史问题：个人分支曾落后 dev 121~250 个 commit，导致合并冲突集中爆发。养成「每天开工先 fetch」的习惯。

## 四、质量门禁（当前只提示，不阻塞）

`.husky/pre-commit` 已接入两个检查，**均为提示模式，不阻塞提交**；`.husky/pre-push` 除这两个提示外，**额外拦截公共分支直推**：

| 脚本 | 检查什么 | 严格模式 |
|------|---------|---------|
| `scripts/check-lint-baseline.mjs` | `vue-tsc` 报错是否**新增** | `LINT_BASELINE_STRICT=1` |
| `scripts/check-herness-size.mjs` | 文档体量是否失控 / 日志是否写回 SOP | `HARNESS_STRICT=1` |
| `.husky/pre-push` 分支保护 | 目标分支属公共分支（`main`/`dev`/`test`/`uat` 等）时**阻塞推送** | 无条件生效 |

**判定标准是「没有引入新增报错」，不是「零报错」**（基线约 190 项 `TS6133`）。判定命令：

```bash
pnpm lint:baseline       # 期望输出「无新增报错」
pnpm harness:check       # 期望输出「文档体量正常」
```

> 后续若接入 GitLab CI，在 CI job 里设 `LINT_BASELINE_STRICT=1` / `HARNESS_STRICT=1` 即可卡住；**当前按团队决策暂不实施**。

## 五、环境变量与敏感信息（🟡 P1 · 已实施）

| 文件 | 处理 |
|------|------|
| `.env.development` / `.env.production` / `.env.test` | **入库并全环境同步**：配置（含调试凭证）一律走 env，各环境文件保持同步；**是否敏感、是否删除由人工判定** |
| `.env.local` | **不入库**，本地私有覆盖 |
| `.env.local.example` | ✅ 已入库，作为模板参考 |

配置值（含调试用 mock token 等）**不写进源码**，统一写入对应环境的 `.env.*`，由 `src/config/env.ts` 的 `appEnv` 中转读取；新增配置项需在**各环境同步**，避免只在单一环境存在。

> **敏感判断与删除由人工负责**：AI 不自动扫描、删除或改写 `.env.*` 中的任何既有配置项，也不代替人工判定某值是否敏感。需要清理时由人工确认后处理（详见 `设计规范速查.md` 四·之二「环境配置中转规则」）。

## 六、文档同步（多人一致性的核心）

多人维护时，「文档与代码脱节」是最隐蔽的坑。本仓库的三层信息架构：

| 内容 | 位置 | 变更频率 | 谁读 |
|------|------|---------|------|
| **工作规则** | `herness/00-SOP.md` | 低 | 每次任务 |
| **现行规范** | `herness/05-共享上下文/*.md` | 低 | 按任务类型 |
| **当期状态** | `herness/05-共享上下文/当前状态摘要.md` | 中（修复即删） | 每次任务 |
| **流水账** | `herness/09-工作日志/YYYY-MM/YYYY-MM-DD.md` | 高 | 需要追溯时 |
| **历史方案** | `herness/02-技术设计/前端/_archive/` | 不变 | 只读参考 |

**落位口诀**：*流水账进日志，规矩进规范，仍有效的结论进摘要，落地完的方案进归档。*

`pnpm harness:check` 会机械校验这条规则（防止日志回流 SOP、已修复条目长期滞留）。

## 九、AI 提交与推送规则（🟡 2026-10-16 定版）

> **定位**：AI 代替人工执行 `git commit` / `git push` 时的权限边界与前置门禁。
> **前置**：本节与 `03-测试/_流程规范.md`、`06-PR审查/_流程规范.md` 配套使用。
> **总原则**：AI **不自动**提交或推送。必须人工明确表达「提交 / commit」「推送 / push」意图后，才进入本节流程。

### 9.1 权限分级

| 动作 | AI 权限 | 说明 |
|------|--------|------|
| 改代码 / 改文档 | ✅ 自动 | 常规任务 |
| 本地 `git commit` | ⚠️ **需人工确认** | 人工说「提交 / commit / 记录一下」后才执行 |
| push 到**个人分支**（`dev-<姓名>`） | ⚠️ **需人工确认** | 人工说「推送 / push」后才执行；确认前先列出将推送的 commit |
| push 到**公共分支**（见 9.2） | ❌ 禁止 | 只能通过 MR 合入 |
| `git push --force` / `--force-with-lease` | ❌ 禁止 | 改写远端历史，风险不可逆 |
| `git reset --hard` 丢弃他人提交 | ❌ 禁止 | 需人工单独授权 |
| 建分支 | ⚠️ 按需 | 命名遵循 9.3；不主动建无意义的分支 |
| 提 MR | ⚠️ 需确认 | 按 `06-PR审查/_流程规范.md` 模板组装后交用户确认 |

**「需人工确认」的判定**：只有人工在对话中明确表达提交/推送意图才触发。
「做完了」「改好了」「继续」等**不构成**提交或推送授权；任务收尾时 AI 应主动汇报改动并**询问**是否需要提交，不得径自执行。

### 9.2 公共分支清单（禁止直推）

`main`、`master`、`dev`、`test`、`uat`、`prod`、`production`、`release`、`hotfix`

- AI push 到上述任一分支会被 `.husky/pre-push` **直接拦截**（唯一会阻塞推送的检查）
- 合入方式：推到个人分支 → 建 MR → 审查合入

### 9.3 分支命名

统一沿用项目现状的 `dev-<姓名>` 格式（例如 `dev-hhr`），AI 不引入第二套前缀体系。

### 9.4 Commit 流程（人工确认后执行）

人工表达提交意图后，按顺序执行：

```bash
git status --short        # ① 汇报待提交文件清单（确认无 dist/ node_modules/ auto-imports.d.ts 误入），等人工确认
pnpm lint:baseline        # ② 期望「无新增报错」
pnpm harness:check        # ③ 期望「文档体量正常」
pnpm test                 # ④ 涉及逻辑变更时必跑
```

### 9.5 Commit 信息规范

复用现有 `commitlint.config.js`（`commit-msg` hook 已阻塞非法格式）。

```
<type>(<scope>): <subject>

type 白名单：feat fix docs style refactor perf test build ci chore revert wip hotfix
scope 可选，建议用目录名：auth / store / controller / composables / herness / config
header ≤ 72 字符，末尾不加句号；body 每行 ≤ 400 字符（中文语境下 200 过窄，400 可容纳完整叙述）
```

**body 必须包含「关联文档」行**，指向当次任务的技术方案或工作日志，保证可追溯：

```
refactor(auth): 统一凭证管理，移除硬编码JWT兜底

收敛 accessToken 读取路径，useUserStore 成为唯一凭证源；
alova beforeRequest 统一注入，高德代理不带凭证。

关联文档: herness/09-工作日志/2026-10/2026-10-16/agent-huanghuanrong.md
```

### 9.6 Push 流程（人工确认后执行）

人工表达推送意图后，按顺序执行：

```bash
git fetch origin
git status                 # 确认无冲突
git log --oneline @{u}..HEAD   # 列出将要推送的提交
```

- 先向人工列出待推送的 commit 清单，**确认后**再推送
- 目标分支不在 9.2 清单内 → 执行推送
- 目标分支在清单内 → 停止，提示走 MR
- 推送后向用户报告 commit hash 列表

### 9.7 hook 现状与边界

| hook | 检查内容 | 是否阻塞 |
|------|---------|---------|
| `commit-msg` | commitlint 格式 | ✅ 阻塞 |
| `pre-commit` | lint 基线 + herness 体量 | ❌ 提示（`\|\| true`） |
| `pre-push` | **公共分支拦截** + lint 基线 + herness 体量 | ✅ 仅分支拦截阻塞，其余提示 |

> pre-commit / pre-push 中的 lint 检查是**提示模式**，真正的门禁由 AI 在 9.4 / 9.6 主动执行命令把关。

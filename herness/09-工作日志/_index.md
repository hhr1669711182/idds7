# 09-工作日志

> **本目录是历史流水账，不是规范。** AI 每次接手任务**不需要**读这里，只在需要追溯「某件事什么时候做的、为什么这么做」时才查。

## 为什么要单独拆出来

`00-SOP.md` 是**每次必读的规则**，工作日志是**高频追加的历史**。两者混在一起会导致：

1. **上下文被吃掉** —— 50 条日志占 `00-SOP.md` 的 83%（59.7KB / 71.5KB），规则只占 17%
2. **多人协作必然冲突** —— 50 条日志在同一张 Markdown 表格里，并行提交时同区间撞车
3. **结论过期** —— 日志里写「实测发现 X 有问题」，问题修好后日志还在说有问题

**拆分后**：

| 内容 | 位置 | 变更频率 | 谁需要读 |
|------|------|---------|---------|
| 工作规则 | `00-SOP.md` | 低 | **每次任务** |
| 当日流水账 | 本目录 | 高（每天追加） | 需要追溯时 |
| 当期真实状态 | `05-共享上下文/当前状态摘要.md` | 中（问题修复即删） | **每次任务** |
| 现行规范 | `05-共享上下文/设计规范速查.md` 等 | 低 | 按任务类型 |

## 目录结构

```
09-工作日志/
├── _index.md              ← 本文件：索引 + 落位规则
└── YYYY-MM/
    └── YYYY-MM-DD/
        ├── agent-<git用户名>.md   ← 每人一个文件
        └── agent-<git用户名>.md
```

**按「日期 + 人」拆分是刻意设计**：多人（含多个 AI agent）并行工作时，每人只写自己 `agent-<git用户名>.md`，
物理上不可能撞车，不需要加锁、不需要约定行号范围、也不需要「先 pull 再改」。

> 旧结构（一个日期一个文件 `YYYY-MM-DD.md`）在多 agent 场景会必然冲突：
> 2026-10-19 当天实测同时有 3 个 agent 的日志条目，append 同一文件导致互相覆盖与误提交。

## 落位规则

```
✅ 写日志   → herness/09-工作日志/YYYY-MM/YYYY-MM-DD/agent-<git用户名>.md（目录和文件没有就新建）
✅ 取用户名 → git config user.name（与提交身份一致，便于按作者追溯）
✅ 同人多次 → 往自己的文件追加，最新条目放最上面
✅ 写规范   → herness/05-共享上下文/设计规范速查.md（长期约束）
✅ 写状态   → herness/05-共享上下文/当前状态摘要.md（仍有效的结论，修复后删除）
✅ 归档方案 → herness/02-技术设计/前端/_archive/

❌ 不要把日志写回 00-SOP.md
❌ 不要写别人的 agent-<用户名>.md 文件（那是他的记录）
❌ 不要在日志里写「以后所有任务都要……」这类规则
❌ 不要在当前状态摘要里留「~~已修复~~」条目（修复即删）
❌ 不要把已落地方案当现行规范读
```

> **判断口诀**：*流水账进日志，规矩进规范，仍有效的结论进摘要，落地完的方案进归档。*

## 提交前自检（多人协作必做）

```bash
git diff --cached -- herness/09-工作日志/
```

- 确认暂存区**只有自己**那一个 `agent-<用户名>.md` 的改动
- 不要用 `git add herness/`（会把他人的日志一并暂存，实测已发生过）
- 要写多个目录就逐个列出路径，不要整目录 add

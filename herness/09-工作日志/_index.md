# 09-工作日志

> **本目录是历史流水账，不是规范。** AI 每次接手任务**不需要**读这里，只在需要追溯「某件事什么时候做的、为什么这么做」时才查。

## 为什么要单独拆出来

`00-SOP.md` 是**每次必读的规则**，工作日志是**高频追加的历史**。两者混在一起会导致：

1. **上下文被吃掉** —— 50 条日志占 `00-SOP.md` 的 83%（59.7KB / 71.5KB），规则只占 17%
2. **多人协作必然冲突** —— 50 条日志在同一张 Markdown 表格里，并行提交时同区间撞车
3. **结论过期** —— 日志里写「实测发现 X 有问题」，问题修好后日志还在说有问题

**拆分后**：

| 内容 | 位置 | 变更频率 | 谁需要读 |
|------|------|---------|---------|
| 工作规则 | `00-SOP.md` | 低 | **每次任务** |
| 当日流水账 | 本目录 | 高（每天追加） | 需要追溯时 |
| 当期真实状态 | `05-共享上下文/当前状态摘要.md` | 中（问题修复即删） | **每次任务** |
| 现行规范 | `05-共享上下文/设计规范速查.md` 等 | 低 | 按任务类型 |

## 目录结构

```
09-工作日志/
├── _index.md              ← 本文件：索引 + 落位规则
└── YYYY-MM/
    └── YYYY-MM-DD.md      ← 一天一个文件
```

**按日拆分是刻意的**：同一天多人提交才可能撞车，跨天几乎不会。这把冲突概率从「每次提交」降到「同一天」。

## 落位规则

```
✅ 写日志   → herness/09-工作日志/YYYY-MM/YYYY-MM-DD.md（今天没有就新建）
✅ 同日多次 → 往同一天的文件追加，最新条目放最上面
✅ 写规范   → herness/05-共享上下文/设计规范速查.md（长期约束）
✅ 写状态   → herness/05-共享上下文/当前状态摘要.md（仍有效的结论，修复后删除）
✅ 归档方案 → herness/02-技术设计/前端/_archive/

❌ 不要把日志写回 00-SOP.md
❌ 不要在日志里写「以后所有任务都要……」这类规则
❌ 不要在当前状态摘要里留「~~已修复~~」条目（修复即删）
❌ 不要把已落地方案当现行规范读
```

> **判断口诀**：*流水账进日志，规矩进规范，仍有效的结论进摘要，落地完的方案进归档。*

## 维护责任

- **追加日志**：完成任何任务后（日志写完即弃，不必精雕细琢）
- **维护 `_index.md`**：跨月时新建 `YYYY-MM/` 目录并在本文件加索引行
- **归档**：季度结束后，可把整月目录整体压缩/合并到 `_archive/`，索引行改为指向归档

## 3. Q1 · 工具链与浏览器自动化方案
### 3.1 先厘清一件易混事实
列出的四个工具，实际上是**同一框架的四个整合包**，不是四个独立工具：
```
@vitejs/devtools                    ← dock 宿主（命令面板 + RPC + 面板容器 + 终端聚合）
  ├─ @vitejs/devtools-vite           ← 插件管线 / 模块 transform 可视化
  ├─ @vitejs/devtools-rolldown      ← 构建分析：模块图 / chunk / asset / 重复依赖 / 插件洞察
  ├─ @vitejs/devtools-oxc           ← oxlint / oxfmt 诊断
  └─ @vitejs/devtools-vitest        ← Vitest UI（测试面板 + 覆盖视图）
```
四个要点：
1. **Vite 8.3 起 Rolldown 已是唯一 bundler**，不存在「再装一个 Rolldown」的选项；`@vitejs/devtools-rolldown` 是构建分析面板，装上即挂在已有 dock 上。
2. 整合包**按需安装**：dock 内显示启动器，点击即装对应包并提示重启 dev server；已装的自动挂载。
3. 宿主版本硬约束 **Vite ≥ 8.3.0**。本项目 `package.json` 声明 `vite ^8.3.0`、实际安装 8.3.0，刚好达门槛。
4. Vue DevTools v9 同样要求 Vite 8.3.0+，且必须在 `vite.config.ts` 配 `devtools: { apply: 'serve' }`，否则插件会打警告。
### 3.2 四个面板对本项目的实际价值
| 面板 | 解决本项目什么问题 | 优先级 |
|------|-------------------|-------|
| **Vite DevTools**（`@vitejs/devtools-vite`） | 本项目插件链很重：`vue` + `vueJsx` + `UnoCSS` + `vite-plugin-cesium(rebuildCesium)` + `AutoImport` + `Components` + `createSvgIconsPlugin`。某个插件悄悄改写模块（Cesium 的 worker/wasm 路径处理、自动导入的 dts 注入）时，现在只能靠猜 | **P0** |
| **Rolldown DevTools**（`@vitejs/devtools-rolldown`） | 依赖体积大（`ol` + `three` + `cesium` + `ol-ext` + `turf` + `jspdf` + `gsap`）。`build:lib` 产出 `dist-lib/openlayers-map.es.js`，需要知道体积来自谁、是否有重复依赖 | **P0** |
| **Vitest UI**（`@vitejs/devtools-vitest`） | 单测可视化运行、失败定位、逐文件覆盖视图 | **P0** |
| **Oxc DevTools**（`@vitejs/devtools-oxc`） | 只想看诊断面板、暂不换 lint 体系时可单独安装 | **P2**（见 §3.4） |
### 3.3 浏览器自动化：Vite DevTools 不是浏览器自动化
| 形态 | 工具 | 能测什么 | 测不了什么 | 适配度 |
|------|------|---------|-----------|-------|
| **A. 组件浏览器测试** | `vitest` + `@vitest/browser` + `@vitest/browser-playwright` | 组件在**真实浏览器**内挂载、交互、截图 | 跨页面流程、真实网络链 | 中：面板类组件适合；OL/Three 组件需 mock 引擎 |
| **B. E2E 端到端** | `@playwright/test` | 跨页面、跨层（view → store → controller → plugins → 引擎）、消息链路、postMessage | 引擎像素级渲染 | **高**：本项目主要回归痛点在跨层链路 |
| **C. 视觉回归** | `@playwright/test` 截图 + 像素对比 | 地图渲染、绘制结果、路径规划线形 | 动态数据一致性 | 低（地图数据动态，基线难稳定），仅固定数据集页面可做 |
推荐组合：**B 为主干（覆盖跨层回归），A 为补充（组件级快速定位），C 仅在固定场景试点**。
### 3.4 Oxc 要不要上：结论与理由
| 维度 | ESLint | Oxc（oxlint + oxfmt） |
|------|--------|-------------------|
| 性能 | JS 实现，全量扫描慢 | Rust 实现，官方与社区数据为 ESLint 的 50–100 倍 |
| 生态成熟度 | 插件最多、规则最全 | 规则集快速追赶中，插件生态薄 |
| 类型感知 | 需 `typescript-eslint` | 需 `oxlint-tsgolint`（生态仍在发展） |
| 对本项目 | `vue-tsc` 已占住类型门禁，再加 ESLint 即**第三套口径** | 同左，边际收益递减 |
**结论：P2，本期不引入 oxlint 运行时，只在需要看诊断面板时安装 `@vitejs/devtools-oxc`。**
理由：
1. 现有硬门禁是 `vue-tsc`，193 个基线报错中绝大多数是 `TS6133` 未用变量——这确实适合 lint 类工具处理，但**更划算的路径是把基线清零**（§7.3），而非新增一套需配置与治理的工具。
2. 「分层铁律」（`core/business/**` 不得 `import 'ol'`）需自定义规则，oxlint 与 ESLint 成本相同；现阶段 herness 文档门禁 + PR 审查已够用。
3. 新增 lint 会立刻产生「新的既有报错」，与 G4「只卡新增」的基线治理思路冲突，拖慢收敛。
> 若团队后续决定引入 oxlint，建议**只开项目特定规则**（分层越界 import、裸 `WebSocket`、裸 `message` 监听、跨层 `any`），不开通用风格规则。

| 风险 | 影响 | 规避 |

## 4. Q2 · 测试体系设计
### 4.1 四层测试模型
本项目不能照搬纯 Web 应用的「单测 80% / E2E 覆盖主流程」模板，因为有两个结构性事实：
1. **渲染底座是引擎**：OL / Three / Cesium 在 Node 环境下无法直接实例化，控制器层大量代码一 import 就需要浏览器环境。
2. **核心价值在跨层链路**：真正的回归风险是「消息进来 → 拦截器归一 → store 分发 → controller 图形指令 → 插件渲染」这条链断掉，而非某个纯函数的某个分支没测。
```
L4 系统集成测试  跨页面 / 跨系统边界（浏览器 ↔ mock 网关 ↔ mock WS ↔ postMessage 宿主）
                 工具：@playwright/test
L3 功能测试      组件级交互 + 业务组件行为（真实浏览器）
                 工具：vitest browser mode (@vitest/browser-playwright)
L2 集成测试      模块间协作：拦截器链、store ↔ controller、service ↔ alova 适配器
                 工具：vitest + jsdom（引擎层 stub）
L1 单元测试      纯函数 / 纯逻辑，零 DOM、零引擎
                 工具：vitest + jsdom
```
### 4.2 每层的范围、落点与门禁
| 层 | 覆盖对象 | 文件落点 | 断言对象 | 环境 | 门禁 |
|----|---------|---------|---------|------|------|
| **L1 单元** | `src/baseComponent/tools/transform.ts`、`src/baseComponent/amap/amapCoordinate.ts`、`src/service/coordinateText.ts`、`src/service/error.ts`、`src/interceptor/unwrap.ts`、`src/interceptor/matcher.ts`、`src/config/mapConfig.ts`、`src/utils/crypto.ts`、`src/utils/storage.ts` | `src/<模块>/__tests__/*.spec.ts` | 返回值 / 边界 / 抛错 | jsdom | **CI 必过**，无豁免 |
| **L2 集成** | `src/interceptor/**`（registry + transforms 全链）、`src/store/useMessageStore.ts`（publish/subscribe + connect 分支）、`src/store/useMapConfigStore.ts`、`src/service/alova.ts`（拦截器行为）、`src/controller/core/generic/**`（stub 引擎后测 DTO 组装） | `src/<模块>/__tests__/*.spec.ts` | 模块协作 + 副作用可观察 | jsdom + 引擎 stub | **CI 必过**，核心模块卡覆盖率 |
| **L3 功能** | `src/components/map/component/**`（circleQueryPanel、routePlanPanel）、`src/components/AddressRobotPanel/**`、`src/components/bottomNav/**`、`src/components/common/**` | `src/components/<组件>/__tests__/*.spec.ts` | 组件行为（按钮禁用、面板展开、解析回填） | 真实浏览器 | 关键组件必过，其余 warn |
| **L4 系统集成** | 跨页面回归：`/map`、`/dispatch`、`/modelAssess`、`/markDraw`、`/amap-demo`；消息链路端到端；postMessage 宿主桥 | `tests/e2e/*.spec.ts` | store 状态、handler 调用、feature id 与坐标 | Chromium + mock 网关 + mock WS | **CI 必过**（回归集） |
> 命名统一：新增测试文件名用 `*.spec.ts`，与遗留 `tests/*.test.ts`（`node:test`）区分。

### 4.4 单测用例设计规范：六类场景
每个被测模块至少覆盖这六类场景：
| 场景类 | 目的 | 本项目典型例子 |
|-------|------|---------------|
| **正常路径** | 主流程跑通 | `parseCoordinateText('113.93, 22.53')` → `[113.93, 22.53]` |
| **边界** | 极值、临界、零、空 | lng ±180 / lat ±90 边界；半径 0；空数组；坐标 0（falsy 陷阱） |
| **异常** | 错误输入、类型错误、依赖失败 | 非法 JSON、`null`、alova 500、业务 `success=false`、WS 断线 |
| **等价类** | 同行为的一类输入只测代表 | 四类坐标文本写法各测一个代表 + 一个非法类 |
| **契约** | 输入输出形状稳定 | `RouteResult \| RouteResult[]` 双形态入参都返回归一结果 |
| **回归** | 锁定已修复 bug | 638m 坐标偏移、`parseRouteFeatures` 数组信封、`amapGcj02ToWgs84` 误用 |
**回归用例是本项目最有价值的用例来源**：`herness/00-SOP.md`「八、工作日志」里每一条 bug 修复记录都是真实现场缺陷，都应反推至少一条回归用例。
**具体规则**：
| 规则 | 说明 |
|------|------|
| R1 | 文件名 `*.spec.ts`，落 `src/<模块>/__tests__/`（co-located，与源码同目录树） |
| R2 | 一个 `it()` 只断言一件事；用例标题格式「给定 X，当 Y，则 Z」 |
| R3 | 断言在**可观察行为**：返回值、抛错、store 状态、handler 调用次数、mock 调用次数 |
| R4 | 用 `toBe(null)` 而非 `toBeFalsy()`；布尔用 `toBe(true/false)` |
| R5 | 浮点坐标用 `toBeCloseTo(expected, 6)`；距离断言显式给容差并注明依据 |
| R6 | 引擎层 import 必须 stub（`vi.mock`），不能让 engine crash 拖垮整个 run |
| R7 | **修复类任务必须补至少一条回归用例**；**新增公共逻辑（utils / interceptor / service / controller DTO）必须带单测** |
| R8 | 用例内禁止真实网络请求（HTTP / WS / 高德代理），需要时用 MSW 或 `vi.mock` |

## 5. 测试落点与配置（Vitest + Playwright）
### 5.1 Vitest 配置方案
`vitest.config.ts`（新建，与 `vite.config.ts` 并列；**不合并进 vite.config.ts**，避免测试依赖污染 dev/build）：
```ts
// vitest.config.ts —— 单元 + 集成层（jsdom），不含浏览器项目
import { fileURLToPath } from 'node:url'
import { defineConfig } from 'vitest/config'
export default defineConfig({
  resolve: {
    alias: { '@': fileURLToPath(new URL('./src', import.meta.url)) },
  },
  test: {
    globals: false,
    environment: 'jsdom',
    include: ['src/**/__tests__/**/*.spec.ts'],
    exclude: [
      '**/node_modules/**',
      '**/dist/**',
      '**/dist-lib/**',
      'src/**/*.browser.spec.ts',
    ],
    coverage: {
      provider: 'v8',
```

### 5.4 GIS 项目的 E2E 断言策略（关键设计）
**核心原则：断言状态，不断言像素。**
地图是 Canvas/WebGL，`expect(locator).toHaveScreenshot()` 在动态地图数据下极不稳定，会产出大量假失败。本项目的 E2E 断言落点：
| 断言层 | 做法 | 示例 |
|-------|------|------|
| **store 状态** | 通过 `window.__IDS_DEBUG__` 暴露 store 快照（仅 dev/test 环境注入），E2E 读取 | 触发检索 → `searchPanelClosed === false` |
| **消息中枢** | 注入 mock WS 消息 → 断言订阅 handler 被调用、事件键匹配 | mock `alarm_call` → 对应 store 状态变化 |
| **DOM 可见性** | 面板类 UI 直接断言 | `routePlanPanel` 里程输入框 value |
| **坐标精度** | 断言 store 内的坐标值（容差 1e-6） | 输入 `113.93, 22.53` → store 中 `[113.93, 22.53]` |
| **服务层** | MSW 拦截 `/bff-client/**` 与 `/a/**` 返回 fixture | mock 高德 regeo 返回 1 条 POI → 断言输入框回填 |
| **渲染结果** | 断言渲染出的 feature id / 坐标，而非截图 | `useBaseSourceStore` 中图层要素数量 |
**调试挂载点设计**（dev/test 环境）：
```ts
// src/lib/index.ts 或 src/main.ts（dev/test 分支）

  ;(window as any).__IDS_DEBUG__ = { stores, controllers, version }
}
```
### 5.5 覆盖率策略与阈值
**核心原则：不追求全局覆盖率数字，只对「可测且高风险」的模块卡阈值。**
| 对象 | 阈值 | 理由 |
|------|------|------|
| 纯逻辑模块（`src/utils/**`、`src/config/**`、`src/interceptor/**`、`src/service/coordinateText.ts`、`src/service/error.ts`、`src/baseComponent/tools/transform.ts`） | **lines ≥ 80%、branches ≥ 75%** | 无 DOM/引擎依赖，纯函数，是回归价值最高的部分 |
| `src/store/useMessageStore.ts` | **lines ≥ 60%** | 有 WS/BC 副作用，但 publish/subscribe 核心可测 |
| `src/controller/core/generic/**` | **lines ≥ 50%** | 需 stub 引擎后测 DTO 组装，工作量较大 |
| `src/components/**`、`src/views/**` | **不卡阈值** | 依赖引擎，组件测试成本高；以 L3 关键组件 + L4 E2E 替代 |
| 全局 | **不卡阈值** | 大面积 `.vue` 组件与引擎绑定层，阈值会逼出无意义的覆盖数字 |
阈值实现（`coverage.include` 白名单 + `coverage.thresholds` 全局阈值）。若要做**分层阈值**，需按 project 分别配置 `coverage.thresholds`，Vitest 4 支持 project 级覆盖配置。
> 当前 `herness/examples/测试策略-示例.md` 已给出初步目标（纯逻辑 ≥ 80%、控制器 ≥ 60%），本节为其正式落地版。

## 6. Q4 · 日志框架方案
### 6.1 结论：需要引入，但要轻量、自研最小封装，不引第三方 APM
**判断依据**：
| 方案 | 优点 | 缺点 | 本项目适配 |
|------|------|------|-----------|
| **自研轻量 logger**（推荐） | 零依赖、体积小、完全可控、与分层架构不冲突 | 需自己实现级别/脱敏/缓冲 | **高** |
| `console` 直接用 | 无需抽象 | 66 处散落、无级别控制、无脱敏、无法按会话回溯 | 低 |
| pino / loglevel 等库 | 现成 | 需适配 Vue/浏览器环境、chaining API 与项目风格不符、体积 | 中 |
| Sentry / APM | 完整监控告警 | 过重（需后端接入、需项目 ID、体积大）、本期无后端配合 | 低 |
**结论**：引入**自研最小 logger**（`src/utils/logger.ts`），核心能力：级别控制 + 命名空间 + 脱敏 + 环形缓冲 + 导出。
### 6.2 Logger 设计
```ts
// src/utils/logger.ts（方案）
type LogLevel = 'debug' | 'info' | 'warn' | 'error'
interface LoggerOptions {
  namespace: string
  level?: LogLevel
  persist?: boolean   // 是否写入环形缓冲（默认 error/warn 为 true）
}
export interface LogEntry {
  ts: number
  level: LogLevel
  namespace: string
  message: string
  data?: unknown
  sessionId: string
  userId?: string
  buildVersion: string
}
class Logger {
  debug/info/warn/error(msg: string, data?: unknown): void
  child(ns: string): Logger          // 派生命名空间，如 logger.child('ws')
  export(): LogEntry[]               // 导出环形缓冲
  clear(): void
  setLevel(level: LogLevel): void
}
export const logger = new Logger()
export const createLogger = (ns: string) => logger.child(ns)
```
**核心能力**：
| 能力 | 设计 |
|------|------|
| **级别控制** | 由环境变量 `VITE_LOG_LEVEL` 控制（`dev` 默认 `debug`，`production` 默认 `warn`）。低于级别的日志直接丢弃，避免生产刷屏 |
| **命名空间** | 每模块一个 logger（`const log = createLogger('ws')`），日志自带来源，排查时不用猜 |
| **脱敏** | 自动过滤 `token` / `Authorization` / `password` / `accessToken` 等敏感 key；坐标与手机号按需保留（业务必需） |
| **环形缓冲** | 保留最近 N 条（默认 200 条），超出丢弃最旧。用于「出问题后现场导出」 |
| **会话标识** | 每条日志带 `sessionId`（页面加载时生成 UUID）+ `userId` + `buildVersion`，便于关联 |
| **导出** | 提供 `exportLogs()` 下载 JSON；配合 §5.4 的 `__IDS_DEBUG__` 挂载点，QA 可一键导出问题现场 |
| **非侵入** | logger 内部最终调用 `console.*`（保留浏览器开发者工具体验），额外写缓冲 |
### 6.3 日志接入点（按优先级）
| 优先级 | 接入点 | 日志内容 | 价值 |
|-------|--------|---------|------|
| **P0** | `src/store/useMessageStore.ts` | WS 连接/断开/重连、消息接收（事件键 + 来源）、拦截器命中/丢弃、订阅/退订 | 跨系统问题排查的第一现场 |
| **P0** | `src/service/alova.ts` | 请求 URL + method + 耗时 + 状态码、业务 code、错误类型（不记 body） | 接口问题定位 |
| **P0** | `src/interceptor/registry.ts` + `matcher.ts` | 拦截器注册、匹配成功/失败、transform 抛错 | 消息「为什么没到业务侧」的核心 |
| **P1** | `src/controller/core/business/**` | 关键控制指令入参摘要（featureId / 数量 / 类型） | 图形指令链路排查 |
| **P1** | `src/plugins/mapPlugins/**` | 地图初始化失败、图层加载失败、引擎异常 | 渲染问题定位 |
| **P2** | 现有 66 处 `console.*` | 逐步替换为 `logger.*`，按目录推进 | 统一风格 + 获得级别控制 |
### 6.4 日志级别使用规范
| 级别 | 用途 | 生产是否开启 |
|------|------|-------------|
| `debug` | 开发调试细节（DTO 全文、循环次数、几何点个数） | 否 |
| `info` | 关键业务节点（WS 连接成功、地图初始化完成、用户登录） | 否（默认 warn） |
| `warn` | 可恢复异常（WS 重连、单次接口失败、配置回退到默认值） | 是 |
| `error` | 不可恢复异常（WS 断开、渲染崩溃、未捕获异常） | 是，且入环形缓冲 |
**约束**：`warn` / `error` 不得打印完整 DTO（可能含人员信息）；只打关键字段与 ID。
### 6.5 与测试日志的关系
- **测试日志**：Vitest / Playwright 自带 reporter，无需 logger 参与。logger 在测试环境应降级为 `error` 且**不入缓冲**（避免污染断言）。
- **AI 生成日志**：herness `00-SOP.md` 工作日志是**人工/AI 协作记录**，不属于运行时日志，不引入框架；保持 Markdown 格式即可（§7.1）。
- **运行日志**：即上述 logger，解决的是「线上/联调现场无法复现」的问题。
### 6.6 日志接入的落地顺序（分三批）
| 批次 | 范围 | 预估工作量 |
|-------|------|-----------|
| **第一批** | `src/utils/logger.ts` + `src/store/useMessageStore.ts` + `src/service/alova.ts` + `src/interceptor/**` | 1–2 人日 |
| **第二批** | `src/controller/core/business/**` + `src/plugins/mapPlugins/**` | 1 人日 |
| **第三批** | 逐步替换现有 66 处 `console.*` | 分散，随改动推进 |

### 10.3 一个必须在设计里说清的技术细节
**测试文件会被 `vue-tsc` 检查**：
```
tsconfig.json include: ["src/**/*.ts", "src/**/*.tsx", "src/**/*.vue", "src/**/*.d.ts"]
```
测试落点 `src/<模块>/__tests__/*.spec.ts` **匹配 `src/**/*.ts`**，所以：
| 后果 | 应对 |
|------|------|
| 测试文件会被 `vue-tsc` 类型检查 | ✅ 期望行为——测试写错类型应报错 |
| 但测试需要的 `vitest` / `@vue/test-utils` 类型不在 `tsconfig` 的 `types` 里 | 需在 `tsconfig.json` 增 `"types": ["vite/client", "vitest/globals"]`（或用显式 import 避免 globals，此时无需改 types） |
| 测试文件的 `noUnusedLocals` 也会生效 | 符合预期，测试里不要留无用变量 |
**结论**：因为本方案采用**显式 import**（`import { describe, it, expect } from 'vitest'`）而非 globals，**无需修改 `tsconfig.json`**。这一点必须写清，否则实施者会误以为要动 tsconfig。
> 反过来说：**不要**在 `vitest.config.ts` 里设 `globals: true`。本方案用显式 import，配置里已明确 `globals: false`。

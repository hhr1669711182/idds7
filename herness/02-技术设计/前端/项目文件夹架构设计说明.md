# 项目文件夹架构设计说明（ids-gis-web）

> **文档定位**：说明本项目**文件夹（目录）架构的设计思想** —— 每个目录为什么存在、被谁依赖、允许依赖谁、能放什么不能放什么。**不描述具体功能实现**，只描述「代码往哪放、依赖往哪流」。
>
> **事实来源**：`src/**` 实测提取；业务契约真相源 `docs/source/**`。
> **适用范围**：整个 `src/**`。
> **撰写时间**：2026-10-10

***

## 一、整体架构思想

### 1.1 一句话概括

> **「视图 / 状态 / 控制 / 底座 / 引擎」五段式 + 「消息中枢」单向管道**：
> 功能代码按业务落位到目录，依赖永远单向向下。

### 1.2 依赖流向（硬约束）

```
┌──────────────────────────────────────────────────────────────┐
│ views / components          视图层                           │
│   只读 store、只调 controller 公开方法                        │
└───────────────┬──────────────────────────────────────────────┘
                ▼
┌──────────────────────────────────────────────────────────────┐
│ store                       状态层（Pinia）                  │
│   业务状态 + 唯一消息总线 useMessageStore                    │
└───────────────┬──────────────────────────────────────────────┘
                ▼
┌──────────────────────────────────────────────────────────────┐
│ controller/core/generic     通用图形控制（零业务）            │
│ controller/core/business    业务控制（只组装通用 DTO）         │
└───────────────┬──────────────────────────────────────────────┘
                ▼
┌──────────────────────────────────────────────────────────────┐
│ plugins/mapPlugins          渲染底座（MapCore + 插件）        │
└───────────────┬──────────────────────────────────────────────┘
                ▼
        OpenLayers / Three / Cesium（引擎，第三方）
```

**铁律**：箭头只能单向向下。任何反向依赖（controller 反向读 store 原始数据、视图层直接 import 引擎类）都是架构缺陷，不是「例外情况」。

### 1.3 代码落位原则

| # | 原则                | 落地例子                                                            |
| - | ----------------- | --------------------------------------------------------------- |
| 1 | **功能 = 目录**       | `views/dispatch/` 是一个功能页，按业务名而非技术名（MVC/Component）分目录            |
| 2 | **按业务分，不按技术分**    | `controller/core/business/CallController.ts` 按业务域归类，而不是按「MVC」归类 |
| 3 | **一份事实只存一处**      | 事件键只在 `const/const.message.type.ts`；图层清单只在 `config/layers.ts`   |
| 4 | **目录名是导航信号，不是权限** | 权限是运行时 concern，落在 `.env` + `appEnv`，不进目录结构                      |
| 5 | **数据方向与代码方向解耦**   | 数据下行（消息）可以横向扇出；代码依赖（import）必须单向                                 |

## 二、目录逐层说明

### 2.1 视图层 `src/views/**` + `src/components/**`

**职责**：路由级页面与可复用 UI 组件。

**允许依赖**：store（只读）、controller（公开方法）、components、assets、composables。
**禁止**：直接 `new OlMap()`、直接操作 renderer、直接 import `ol/**` 的渲染类。

| 子目录                                              | 业务含义                  | 状态  |
| ------------------------------------------------ | --------------------- | --- |
| `views/dispatch/`                                | 调度主页面（核心业务页）          | 核心  |
| `views/dispatch1/`                               | 调度页面第二版（迁移中）          | 迁移中 |
| `views/modelAssess/`                             | 模型研判（Three 3D + 倾斜摄影） | 核心  |
| `views/markDraw/`                                | 标绘演示页                 | 演示  |
| `views/amap/`                                    | 高德 API 演示             | 演示  |
| `views/test/`                                    | 测试页                   | 演示  |
| `views/home.vue` / `region.vue` / `building.vue` | 首页 / 区域 / 楼宇          | —   |

`src/views/<功能>/` 内部允许再分 `components/`（页面私有组件）、`composables/`（页面私有组合式逻辑）、`styles/`（页面样式）、`model3d/`（该功能的 3D 构建逻辑）。**页面私有的东西放页面目录内，跨页面复用的上提到** **`src/components/`** —— 这是本项目划分 private vs shared 的唯一标准。

`src/components/` 是跨页面共享的 UI 层，按业务域分目录（`AddressRobotDrawer`、`MarkDraw`、`BIM`、`Modals`、`map`、`Icon`…）。注意 `components/map/` 与 `baseComponent/OpenlayersMap/` 的区别：前者是**地图相关 UI 控件与工具面板**（MapTools、图层面板），后者是**地图渲染宿主**（见 2.4）。

### 2.2 状态层 `src/store/**`

**职责**：跨组件业务状态 + **唯一消息总线**。

| 文件                   | 职责                                                                                                                                |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `useMessageStore.ts` | **消息中枢**：所有 WS / postMessage / BroadcastChannel 收发必经此处的 `publish` / `subscribe`                                                   |
| `piniaPersist.ts`    | 持久化封装（`pinia-plugin-persistedstate`），统一走它而不是散写 localStorage                                                                       |
| `index.ts`           | store 统一出口，其他模块从 `@/store` 引入                                                                                                     |
| `useXxxStore.ts`     | 各业务域状态：`useBaseSourceStore`（底图）、`useLayersStore`（图层）、`useUserStore`（登录态）、`useMapStore` / `useDispatchMapStore` / `useModalStore`… |

**关键设计**：消息总线**不是**普通 store，它是 `defineStore` setup 风格里唯一承载「跨系统 IO 生命周期」的地方 —— WS 连接、postMessage 监听、BroadcastChannel 绑定都在这里挂载与销毁。所以 store 层天然需要知道 transport 层（`hooks/`），这是**唯一允许 store 引 hooks 的场景**。

**注意**：`useMessageStore916.ts` 是历史版本，当前生效的是 `useMessageStore.ts`（见 2.9）。

### 2.3 控制层 `src/controller/**`

**职责**：把业务语义翻译成图形指令，隔离视图层与引擎。

```
controller/
├── core/
│   ├── generic/     通用图形控制：view / geometry / spatial / kinematic —— 只执行图形指令，无业务语义
│   ├── business/    业务控制：alarm / call / dispatch / tracking / duty / config / addressRobot
│   ├── io/          输入输出控制：InputController（收消息→调 generic）/ OutputController（视图指令→发消息）
│   └── protocol/    跨层 DTO interface（Generic / Business / IO 三份）
├── map/index.ts     地图系统对外发布订阅门面
├── three/index.ts   三维系统对外发布订阅门面
└── index.ts         统一导出
```

| 规则        | 说明                                                  | 正确做法                      |
| --------- | --------------------------------------------------- | ------------------------- |
| 通用控制层零业务  | `core/generic/**` 不得出现 alarm/call/dispatch 等业务词     | 业务判断放 `core/business/**`  |
| 业务控制层不碰引擎 | `core/business/**` 不得 `import 'ol/...'` 或 `'three'` | 只用注入的 `genericController` |
| DTO 唯一来源  | 控制器方法入参必须是 `core/protocol/**` 的 interface           | 禁止用 `any` 承接跨层数据          |
| 新控制器必须登记  | 新建 `XxxController` 必须在所属 `index.ts` `export *`      | 并回写 `05-共享上下文/项目结构速查.md`  |

**`protocol/`** **为什么单独存在**：跨层数据如果用 `any` 承接，编译器无法在编译期发现「业务层改了字段，视图层还在读旧字段」。把 DTO 收敛到 `protocol/**` 三个文件，让「跨层边界」变成一条**有类型守门的线**，而不是靠人记住。

**`map/index.ts`** **/** **`three/index.ts`** **门面为什么存在**：它们是**跨系统发布订阅门面**——组件订阅消息必须经它们（或 `useMessageStore().subscribe`）暴露的 `onXxx`，而不是直接 `store.subscribe` 到处散订阅。这样订阅点的意图（我要收哪类事件）在门面文件里一目了然，也便于统一加埋点/门控。

### 2.4 渲染底座 `src/baseComponent/OpenlayersMap/**` 与 `src/plugins/mapPlugins/**`

这两个目录都在「引擎之上」，但角色不同，**不要混淆**：

| <br /> | `baseComponent/OpenlayersMap/`                             | `plugins/mapPlugins/`              |
| ------ | ---------------------------------------------------------- | ---------------------------------- |
| 角色     | **地图宿主组件 + 业务装配**                                          | **通用可复用渲染底座**                      |
| 形态     | Vue 组件（`map.vue` / `dispatchMap.vue` / `drawMap.vue`）+ 工具类 | 纯 TS，框架无关（`MapCore` + 插件）          |
| 依赖     | 依赖 controller、store、components                             | **不依赖任何业务**，只依赖 `ol/**`            |
| 复用性    | 项目内专用                                                      | 通过 `src/lib/index.ts` 对外导出，供宿主项目调用 |
| 业务耦合   | 有（调度、来电、警情…）                                               | 无（零业务）                             |

`baseComponent/OpenlayersMap/` 内部职责：

| 文件                                              | 职责                                                               |
| ----------------------------------------------- | ---------------------------------------------------------------- |
| `map.vue` / `dispatchMap.vue` / `drawMap.vue`   | 三套地图宿主组件（各自装配不同业务场景）                                             |
| `baseSource.ts`                                 | 底图图源注册表（高德/百度/天地图/谷歌/离线），`createBaseSourceLayer` 统一出口            |
| `layers.ts`                                     | 图层名常量 + 图层工厂（`AMAP_LAYER` / `VECTOR_LAYER` / `GRID_LAYER` / 水印层） |
| `const.map.ts`                                  | 地图常量（中心点、缩放级别、水印文案）                                              |
| `startup.ts`                                    | 底图就绪等待（`waitForBaseMap`），避免业务图层早于底图就绪                            |
| `FeatureClickQuery.ts` / `JurisdictionQuery.ts` | 要素拾取 / 辖区查询交互插件                                                  |
| `useMapPopups.ts`                               | 气泡管理（车辆/警情/站点）                                                   |
| `mountPointLayer.ts` / `mountPolygonLayer.ts`   | 点/面图层挂载工具                                                        |

`plugins/mapPlugins/` 内部结构（详见其 `README.md`）：

```
MapCore（Map 生命周期 + 插件容器：use/get/remove/destroy）
└── plugins/  9 个能力插件，各自 key 唯一
    ├── useBaseMap      底图管理（register/setActive/getActive）
    ├── useCoreControl  控件管理（缩放/全屏/比例尺/鹰眼）
    ├── useMapStatus    图层与要素状态管理
    ├── useOverlay      弹窗管理
    ├── useDraw         绘图工具链
    ├── useFeatureStyle 样式工厂与缓存
    ├── useRoutePlan    路径规划（planner 注入解耦）
    ├── useBusUpWMS     WMS 上图
    └── useMapUtils     常用工具（flyTo / geocode）
```

**设计思想**：`MapCore` 是「地图的依赖注入容器」，插件通过 `.use()` 注册、`.get()` 取回，`.destroy()` 统一销毁。这样每个能力模块的 `dispose()` 都由框架兜底调用，避免漏解绑。业务能力（路径规划、WMS）通过**注入**（`planner(req)`、`request(input)`）对接不同 API，插件本身零业务。

### 2.5 消息与 IO 层 `src/hooks/**`、`src/interceptor/**`、`src/register/**`

这是本项目**最有特色的一组目录**，共同构成「跨系统通信」体系。

```
外部消息源
  WebSocket（useWebSocket.ts）      postMessage（usePostMessage.ts）    BroadcastChannel（useBroadcastChannel.ts）
        │                                    │                                   │
        └────────────────────────────────────┴───────────────────────────────────┘
                                     ▼
              register/initMessage.ts（统一注册入口，App.vue onMounted 调用）
                                     ▼
                    store/useMessageStore.ts（唯一消息总线）
                    publish（发送） / subscribe（订阅，返回取消函数）
                                     ▼
                    interceptor/registry.ts（拦截器链，按 priority 升序）
                      ├─ unwrap.ts    消息体归一（JSON parse、大小写归一）
                      ├─ matcher.ts   模板匹配（topics / notifyType / eventName）
                      └─ transforms/   业务归一（seat / alarm / alarmCall / carLocation / dispatchers）
                                     ▼
              Envelope → inbox/lastBySystem → triggerSubscriptions → useMessageStore().subscribe → 组件 handler
```

#### `hooks/` —— transport 封装

| 文件                         | 职责                                                                                             |
| -------------------------- | ---------------------------------------------------------------------------------------------- |
| `useWebSocket.ts`          | `WebSocketClient` 类：多实例、自动重连、心跳保活、`initSend` 订阅声明                                              |
| `useBroadcastChannel.ts`   | `BroadcastChannelClient` 类：同源多标签页广播，结构对齐 `WebSocketClient`                                     |
| `usePostMessage.ts`        | postMessage 收发组合式封装（`useListenParentMessage` / `usePostChildMessage` / `usePostParentMessage`） |
| `useRouteMetricsWorker.ts` | Web Worker 封装（高频轨迹指标计算）                                                                        |
| `useEncryptedStorage.ts`   | 加密存储                                                                                           |
| `useDesign.ts`             | 设计模式相关辅助                                                                                       |

**设计思想**：transport 层只关心「字节怎么收发」，**不关心消息是什么业务**。业务语义一律留在 `interceptor/transforms/`。这样换 transport（WS 换 BroadcastChannel）不影响任何业务代码 —— 上一轮加 `useBroadcastChannel` 就是这个设计的直接收益。

#### `interceptor/` —— 消息归一

| 文件                                                    | 职责                                                                                  |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `types.ts`                                            | `MessageInterceptor` / `InterceptorContext` / `InterceptorOutput` / `SubscribeRule` |
| `registry.ts`                                         | 注册 + 按 priority 升序链式执行 + 结果收集                                                       |
| `matcher.ts`                                          | 模板匹配（`topics` / `notifyType` / `eventName` 逐级兜底）                                    |
| `unwrap.ts`                                           | 消息体归一（`content`/`customContent` JSON parse、key 大小写归一）                               |
| `install.ts`                                          | `installDefaultInterceptors()` 默认拦截器装配（由 store 首次 `ingest` 惰性安装）                    |
| `transforms/seat.ts`                                  | SEAT 泛订阅，`dispatch: 'multi'`，二次分发到多个内部事件键                                           |
| `transforms/alarm.ts` `alarmCall.ts` `carLocation.ts` | CUSTOM 业务归一                                                                         |
| `transforms/dispatchers/`                             | 二次分发器（`addressRobot` / `locateCall`）                                                |

**设计思想**：服务端下行消息格式不稳定（字段大小写不一、内容可能包 JSON 字符串、一条消息可能映射多个内部事件），所以在**进入 store 分发前**用可插拔的拦截器链归一。业务归一逻辑与 transport、与 store 全部解耦，加一个新业务只需加一个 transform 文件 + 在 `install.ts` 注册。

#### `register/` —— 启动期装配

`initMessage.ts` 在 `App.vue` 的 `onMounted` 里被调用（与 `initUserStore`、`initPageConditionListener` 一起注册），负责在 Pinia 激活后装配全部 transport：

```ts
const registrations = [initUserStore, initMessage, initPageConditionListener]
```

**为什么放** **`register/`** **而不是** **`hooks/`**：hooks 是「可复用的能力」，register 是「**这个应用启动时要跑一次的装配清单**」。装配顺序有依赖（必须 Pinia 先激活），把它显式建模成一个目录，避免散落在 `main.ts` / `App.vue` 里变成不可见的副作用。

### 2.6 服务层 `src/service/**` + `src/apis/**`

```
composables/useAlova → service/alova.ts（统一实例，token 注入、错误归一）
                              │
                              ▼
                     service/methods/*.ts（业务接口方法，按业务域分文件）
                              │
                              ▼
                     apis/*.ts（图层/高德/路由等第三方接口封装）
```

| 目录/文件                                      | 职责                                                                                                             |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| `service/alova.ts`                         | 主 HTTP 实例（请求拦截注入 token、响应拦截 `toAppError`）                                                                      |
| `service/alovaGeo.ts` / `alovaMapProxy.ts` | 地理服务 / 地图代理专用实例                                                                                                |
| `service/error.ts`                         | 统一错误体系（`AppError` / `ERROR_CODES` / `toAppError`）                                                              |
| `service/geoserver.ts`                     | GeoServer WMS/WFS 封装                                                                                           |
| `service/methods/`                         | 业务接口方法（`alarm` / `auth` / `dispatch` / `dispatchVehicles` / `unclosedIncidents`…），入参响应类型统一在 `methods/types.ts` |
| `apis/`                                    | 第三方 API（`amap` / `layers` / `router` / `auth`）                                                                 |

**`service/`** **与** **`apis/`** **的区别**：前者是**自家后端**（统一实例、统一错误体系、走 `alova`），后者是**外部服务**（各自的调用方式，不强制走统一实例）。不要在 `apis/` 里新建业务后端接口。

**设计思想**：错误处理**只在** **`service/error.ts`** **定义一次**。请求静默靠 `meta: { silent: true }` 配置，不在业务代码里 try/catch 打补丁。

### 2.7 配置与常量 `src/config/**` + `src/const/**`

两者都是「静态事实的存放处」，但语义不同：

| <br /> | `config/`                                                  | `const/`                                                                   |
| ------ | ---------------------------------------------------------- | -------------------------------------------------------------------------- |
| 语义     | **配置**（可被环境覆盖、有结构、有 schema）                                | **常量**（编译期确定、无环境差异）                                                        |
| 例子     | `env.ts`（环境变量读取）、`layers.ts`（图层清单）、`mapConfig.ts`（图层运行时结构） | `const.message.type.ts`（事件键）、`const.map.ts`（中心点/缩放）、`const.common.ts`（主题色） |
| 读取方式   | `appEnv.xxx` / `getLayerConfig(id)`                        | `MESSAGE_EVENT_KEY.xxx` / `THEME_COLOR.NIGHT`                              |

**硬约定**：环境变量**只经** **`src/config/env.ts`** **的** **`appEnv`** **读**，不直接 `import.meta.env`（除 `env.ts` 内部）。这让「哪些环境变量存在、什么类型、什么默认值」在一个文件里一目了然，也让「换环境」只需要改 `.env.*` 文件。

`mapConfig.ts` 是值得单独说明的一例：它是**运行时三层结构**（组 group → 分类 category → 资源 resource）的构建器，从 `config/layers.ts` 的扁平清单加上 localStorage 保存的开关状态组装而成。「扁平清单（事实）+ 运行时结构（状态）」分离，是本项目处理「大量可切换图层」的手法。

### 2.8 组合式逻辑 `src/composables/**`

**职责**：跨组件复用的响应式逻辑。与 `hooks/` 的区别：

| <br />    | `hooks/`                               | `composables/`                                              |
| --------- | -------------------------------------- | ----------------------------------------------------------- |
| 关注点       | **IO / 传输 / 基础设施**                     | **业务状态 / 组件行为**                                             |
| 是否 Vue 感知 | 否（普通 TS 类或函数）                          | 是（用 `ref` / `computed` / `watch` / 生命周期钩子）                  |
| 例子        | `useWebSocket` / `useBroadcastChannel` | `useCarFeatures` / `useUnclosedIncidents` / `useResponsive` |

`composables/` 内部分两类落位：

- **跨页面共享**：`useCarFeatures`、`useSSRKFeatures`、`useFireStations`、`useIncomingCallFeatures`、`useUnclosedIncidents`、`useResponsive`、`useCurrentMap`、`useAlova`、`useAlarmHotspot` —— 放 `src/composables/` 根。
- **页面私有**：`views/modelAssess/composables/useThreeController.ts`、`useThreeScene.ts` —— 放页面目录内，不上提。

`composables/three/fontLoader.vue` 与 `composables/Swiper/` 是少数「目录里不全是 `.ts`」的例外（Vue 组件与样式），说明 composables 目录的准入标准是「Vue 组合式逻辑」而非「必须是 `.ts`」。

### 2.9 路由 `src/router/**` 与布局 `src/layout/**`

- `router/index.ts` 路由表、`router/constants.ts` 路由常量、`router/guard/` 路由守卫（登录态、动态路由）
- `layout/MainLayout.vue` 主布局壳（侧边栏/头部/内容区）

**设计思想**：路由常量与路由表分文件，是为了让「路由路径」成为**一份事实**——菜单、面包屑、守卫都从同一处取，改路径不会漏改。

### 2.10 类型 `src/types/**` 与垫片 `src/shims/**`

| 文件                                            | 职责                                                          |
| --------------------------------------------- | ----------------------------------------------------------- |
| `types/message.ts`                            | `MessageEnvelope<T>` 消息信封定义（跨层消息的核心类型）                      |

### 2.13 库模式与应用模式（双形态）

`package.json` 的两个构建脚本对应两种消费形态：

| 形态 | 命令                        | 入口                       | 用途          |
| -- | ------------------------- | ------------------------ | ----------- |
| 应用 | `pnpm dev` / `pnpm build` | `index.html` → `main.ts` | 独立运行的前端应用   |
| 库  | `pnpm build:lib`          | `src/lib/index.ts`       | 作为库嵌入其他宿主项目 |

`src/lib/index.ts` 的 `mountApp(options)` 是库模式的唯一入口：内部完整初始化 Vue App + Pinia + 路由 + 全局指令 + 可选 `hostEmitter` 通信桥，返回 `{ app, unmount }`。库模式下地图能力通过 `export * from '@/plugins/mapPlugins'` 对外暴露 —— **这也是** **`mapPlugins/`** **必须零业务的原因**（它是库的一部分）。

## 三、横切关注点：贯穿目录的约定

### 3.1 消息协议：改一处必须改三处

| 改什么                                                | 同步更新                            |
| -------------------------------------------------- | ------------------------------- |
| 事件键（`const.message.type.ts` 的 `MESSAGE_EVENT_KEY`） | `docs/source/07-协议事件清单.md`      |
| 跨层 DTO（`controller/core/protocol/**`）              | `docs/source/协议层DTO Schema.tsd` |
| 消息通道（`MESSAGE_CHANNEL`）                            | `herness/05-共享上下文/消息协议速查.md`    |

破坏性协议变更还要升 `MESSAGE_PROTOCOL_VERSION`。

### 3.2 订阅解耦：订阅必须返回取消函数

所有 `onXxx(handler)` 与 `store.subscribe(...)` 都返回取消函数，组件在 `onUnmounted` 调用。**这是防止内存泄漏的唯一约定** —— 因为订阅注册在模块级 `Map` 里，组件卸载不会自动清理。

### 3.3 环境变量：只经 appEnv

现状（`initMessage.ts` 仍是旧写法，直接读 `import.meta.env`）：

> 当前散落写法：`const isUseWS = import.meta.env.VITE_USE_WS === 'true'`

目标写法（`appEnv` 已集中收敛的环境变量，参照 `useBroadcastChannel` 的做法）：

```ts
// 1) 在 src/config/env.ts 的 appEnv 中声明 useWs
// 2) 业务侧统一读取
const isUseWS = appEnv.useWs
```

> **目前** `appEnv` 里只有 `useMock` / `useBroadcastChannel` / `broadcastChannelName` 等已收敛项；`VITE_USE_WS` 与 `VITE_USE_POSTMESSAGE` 仍散落在 `initMessage.ts`，属待收敛项（见「六、已知不一致」）。

### 3.4 坐标系：协议层 WGS84

协议层与服务层统一 **WGS84** **`[lng, lat]`**；进入渲染层前由底座转换（`utils/coordTransform.ts`）。视图层和 controller 之间不出现投影坐标。

### 3.5 类型门禁：`pnpm lint` 是类型检查不是 ESLint

项目**无 ESLint、无单元测试框架**。`pnpm lint` = `vue-tsc --noEmit`，基线约 193 个既有报错（绝大多数 `TS6133` 未用变量）。**判定标准是「没有引入新增报错」，不是「零报错」**。

## 五、决策记录：为什么这么设计

| 决策                                                        | 理由                                            | 代价                                            |
| --------------------------------------------------------- | --------------------------------------------- | --------------------------------------------- |
| 通用层与业务层**物理分离**（generic / business 两个目录）                  | 让「这个能力有没有业务语义」在**目录层面**就可判读，而不是靠 review 时通读代码 | 多一层目录，跨业务复用要判断归哪边                             |
| `protocol/` 单独成层                                          | 跨层数据的类型边界变成编译期可查的东西                           | DTO 与实际实现可能漂移，需要同步维护                          |
| 消息总线唯一出口（`useMessageStore`）                               | 收消息可统一拦截、可埋点、可门控（如 `setIngressGate`）          | 所有 transport 都要经过 store，transport 层被 store 引用 |
| `hooks/`（IO，无 Vue 依赖）与 `composables/`（业务，有 Vue 依赖）分家      | 前者可被非组件场景（store、register）直接调用，后者依赖组件生命周期      | 两套命名，初期需要判断归属                                 |
| `register/` 显式建模启动装配                                      | 装配顺序有依赖（Pinia 先激活），集中可见                       | 每次新增启动逻辑要记得在 `App.vue` 注册                     |
| `baseComponent/OpenlayersMap/` 与 `plugins/mapPlugins/` 分家 | 前者项目内业务装配，后者零业务可对外做库                          | 两套地图抽象并存，理解成本                                 |
| `mapPlugins` 插件通过 `.use()/.get()/.destroy()` 注入           | 插件 `dispose()` 由 `MapCore` 统一兜底，避免漏解绑         | 需要理解「容器 + 插件」心智模型                             |
| `config/`（配置）与 `const/`（常量）分家                             | 前者可被环境覆盖、有 schema；后者编译期确定                     | 边界模糊文件（如 `config/layers.ts`）需要判断              |
| 图层「扁平清单 + 运行时结构」分离（`config/layers.ts` → `mapConfig.ts`）   | 支持大量可切换图层的排序/开关状态持久化，且不污染事实清单                 | 两层结构转换代码（`buildLayerGroups`）                  |

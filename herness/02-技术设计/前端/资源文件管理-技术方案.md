## 3. 目录命名决策（2026-10-19 修订）

初稿曾提议新建 `src/resources/` 作为统一资源根，经讨论后**改为沿用 `src/assets/`**。理由：

- `assets` 是 Vue/Vite 社区通行叫法，团队无需学新词，也不与 `vite.config.ts` 里的 `build.assetsDir`（默认 `assets`，指**产物目录**）抢同一概念的两个含义。
- 本项目真正的痛点不是目录叫什么，而是 `src/assets/` 当前是根目录平铺 20 个文件、底下三个子目录各叫各的（`file` / `icons` / `svg`）、`file/` 里还塞着无人引用的 tif。**理顺内部分类比改目录名值钱得多**。
- 撞名问题（`src/assets/` 与 `src/components/map/assets/` 同名不同物）通过收敛到单一根 + 分类子目录解决，无需靠改名规避。

结论：**沿用 `src/assets/` 作为唯一资源根**，内部按 §5.1 分类。`assetPaths` / `assetUrl` / manifest 校验等配套设计与此无关，不受影响。

## 4. 设计目标

1. **单一落点**：所有资源有明确归属目录，一眼能判断「该放哪」。
2. **区分「打包资源」与「运行期资源」**：前者进产物并带哈希（可缓存、可压缩），后者通过常量层解析 URL。
3. **路径不硬编码**：3D 模型、字体等运行期资源通过 `assetPaths` 常量层解析，改目录只改一处。
4. **可校验**：资源清单（manifest）与校验脚本纳入 `pnpm harness:check`，路径写错/文件缺失在门禁就暴露。
5. **兼容双形态**：`pnpm build`（base `./`）与 `pnpm build:lib`（base `/`，宿主挂载）都能正确解析资源 URL。
6. **不改业务语义**：迁移批次只改路径与落点，不改功能行为，符合「存量不改、新增从新」。

### 5.2 三条放置铁律

| 铁律 | 判定 | 落点 |
|------|------|------|
| **R1 编译期资源** | 需要被 `import` 成模块（模板 `:src`、`new Image()`、JSON 数据） | `src/assets/**`，**必须**经 `@/assets/...` 引用，走 Vite 哈希 |
| **R2 运行期资源** | 只能由 URL 加载（`loader.load()`、`fetch`、`TextureLoader`、字体 JSON） | 也放 `src/assets/**`（带哈希、构建可识别），但**必须**经 `assetPaths` 拼 URL；**禁止**代码里写 `'/model3d/xxx'` 字面量 |
| **R3 免编译资源** | 部署期要被替换、被外部直接 URL 访问、或是 HTML/配置/文档样例 | `public/**`，且必须在 manifest 标注 `publicLiteral: true` 与 `keepReason` |

补充规则：

- **命名**：目录 kebab-case；新增资源文件名 kebab-case，存量保持原名不改。
- **大小阈值**：单文件 > 500 KB 且非运行期必需 → 登记 manifest 并评估外置；> 5 MB 必须在 manifest 写 `keepReason`。
- **重复文件**：同 sha256 出现在两个不同路径 → 视为 bug，manifest 校验报错（除非显式 `duplicateOf`）。
- **二进制声明**：`src/assets/**` 与 `public/**` 的二进制扩展名一律进 `.gitattributes`。

### 5.3 `assetPaths` 常量层设计

```ts
// src/const/assetPaths.ts（新增；业务代码不直接读 import.meta.env）
import { appEnv } from '@/config/env'

/** 运行期资源基础路径。env.ts 内从 import.meta.env.BASE_URL 读出，应用形态 './'、库形态 '/' */
const BASE = appEnv.assetBase

export const ASSET_CATEGORY = {
  model: `${BASE}assets/models`,
  font: `${BASE}assets/fonts`,
  tile: `${BASE}assets/tiles`,
  video: `${BASE}assets/video`,
} as const

/** 语义化键 → URL；改文件名/目录只改这一处 */
export const assetUrls = {
  fireTruck: `${ASSET_CATEGORY.model}/xf_fire_truck.glb`,
  fireFighter: `${ASSET_CATEGORY.model}/xf_firefighter.glb`,
  buildingGltf: `${ASSET_CATEGORY.model}/B370921843501063A0.gltf`,
} as const
```

配套 `src/utils/assetUrl.ts`：

| 函数 | 用途 |
|------|------|
| `resolveAssetUrl(url)` | 给遗留的 `loader.load` 补 `BASE` 前缀（过渡期兜底） |
| `loadJsonAsset<T>(url)` | 懒加载 + `safeJsonParse`（复用 `@/utils` 公共工具） |
| `isAssetMissing(url)` | 资源存在性探测，供 3D 加载失败降级提示 |

> 环境变量规则：按 `设计规范速查.md`「环境配置中转规则」，`BASE_URL` 只在 `src/config/env.ts` 内读一次，业务侧一律走 `appEnv`。

### 5.4 资源清单与校验

`scripts/manifest-assets.mjs` 做四件事，接入 `pnpm harness:check`：

1. 扫描 `public/**` + `src/assets/**` + `src/**` 内的资源文件（扩展名白名单）。
2. 生成 `docs/asset-manifest.json`：`{ path, bytes, sha256, kind, runtimeUrl, publicLiteral, keepReason, refs }`。
3. 校验三条：
   - **R2 合规**：代码里 `loader.load('/…')` / `TextureLoader.load('/…')` / `fetch('/…')` 的字面量必须能在 manifest 中登记，否则报错并提示改用 `assetPaths`。
   - **重复检测**：同 sha256 出现在两个路径 → 报错（除非 `duplicateOf`）。
   - **无引用检测**：`refs` 为空且未标 `publicLiteral`/`keepReason` → 警告（不阻断，删除属人工决策）。
4. 输出体积报告（分目录/分类 MB 汇总），供回写 `herness/05-共享上下文`。

## 7. 特殊处置建议（需人工确认）

> ⚠️ **2026-10-19 清理事故与修正（重要教训，勿重蹈）**
>
> 首轮按「重复 + 零引用即删」清掉 20 个文件、释放 61.2 MB，随后人工复核发现**部分误删并已恢复**。
> 根因有两条，都不是「扫描器不够聪明」，而是判断口径本身错了：
>
> 1. **「代码零引用」不构成可删证据。** `style/icons.ts::getCommonAlarmIconSrc` 用
>    `${colorType}-${type}.svg` **动态模板拼接**文件名（`red-fire.svg` / `blue-rescue.svg` …），
>    按字面量搜代码永远搜不到，于是 6 个实际在用的图元被判成零引用。
> 2. **运行期资源不进 import 图。** `.tif` 瓦片、`.gltf` 贴图由地图引擎 / 瓦片服务按 URL 加载，
>    代码里本就不出现。它们「零引用」是事实，但「零引用」≠「没人用」。
>
> **修正**：`scripts/manifest-assets.mjs` 的零引用提示已补免责说明，并在 `KEEP_REASONS`
> 显式登记动态拼接的图标组（9 个 color×type 组合）；`tests/unit/assetCleanup.spec.ts`
> **不再锁死「哪些文件该删」**（初版那么写导致人工一恢复就红），改为只守底线：
> 运行期模型不得误删、gltf 组整组保留、字体与免编译资源不得误删。
>
> **判定口诀**：*零引用只是线索，删除要人工确认；文件名可能由模板拼出的，先登记再动。*
>
> **最终留存**：实际删除 9 个文件（重复 fav 两份、`xf_fire_truck2.glb`、两份 tif 等），
> 资源总量 **62.18 MB / 91 个文件**（治理前 150.72 MB / 99 个），详见下表逐项标注。

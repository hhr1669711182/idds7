### 3.2 分支模型治理（P1，本月内）

#### 建议的最小分支模型

```
main          ← 稳定版（可部署），受保护，禁止直推
  ↑
dev           ← 集成分支（唯一主干），所有 MR 的目标分支
  ↑
  ├─ feature/<用户名>-<简述>     如 feature/yf-路径规划优化
  ├─ fix/<用户名>-<简述>         如 fix/hhr-坐标偏移
  └─ chore/<用户名>-<简述>       如 chore/cxq-基线收敛
```

#### 落地方案

| 步骤 | 动作 | 风险 |
|------|------|------|
| 1 | 在 `AGENTS.md` 增一节「分支与提交约定」 | 无 |
| 2 | `main` / `dev` 设为 GitLab **protected branch**，禁止直推 | 需 GitLab 管理员配合 |
| 3 | MR 唯一目标分支 = `dev`；关闭直推 `dev` | 需配置 push rules |
| 4 | 与作者确认后清理僵尸分支（`dev-yf` 落后 250、`dev-zh` 落后 176、`dev-guizhou` 落后 142、`dev-cxq` 落后 121） | ⚠️ **需作者确认，方案不做自动删除** |
| 5 | `main` 改为「dev 的稳定快照」：发版时从 `dev` merge 到 `main` | 需团队约定发版节奏 |
| 6 | 确认后删除临时分支（`Building3D-ljh`、`dispatch-ljh`、`dev-clearstorage`、`dev-interfacetest`） | ⚠️ 需确认是否含未合并代码 |

> 清理的前置校验：`git log origin/dev..origin/<branch>` 若为空且作者确认可弃，才可删。**本方案不提供自动删分支脚本**，因为误删不可逆。

### 3.3 门禁治理：从「靠自觉」到「机器强制」（P1）

这是同步一致性的核心机制。三层门禁，按反馈速度递增：

```
L1 本地即时（husky pre-commit，秒级）
  · lint 基线 diff（scripts/check-lint-baseline.mjs）
  · 协议一致性检查（scripts/check-protocol-sync.mjs）

L2 MR 门禁（GitLab CI + CODEOWNERS，分钟级）
  · pnpm lint:baseline / pnpm test / pnpm build
  · 协议一致性 + 文档时效性检查
  · CODEOWNERS 强制指定审查人

L3 分支保护（protected branches）
  · main / dev 禁止直推，必须走 MR
  · 必须通过 L1 + L2 才能合并
```

> ⏸️ **决策 #5（2 approvals + CODEOWNERS）已确认但暂不实施**：当前仓库无 `.gitlab-ci.yml`、无 CODEOWNERS、dev/main 未设 protected branch，因此不会触发任何审批。L2 / L3 需 GitLab 管理员配合，本次不落地。**L1（husky pre-commit）是本地的，不需要 GitLab 任何配置，建议优先实施。**

#### L1：新增 `.husky/pre-commit`

```sh
#!/usr/bin/env sh
. "$(dirname -- "$0")/_/husky.sh"

# 类型门禁：只卡新增，不卡既有基线
node scripts/check-lint-baseline.mjs

# 协议一致性：事件键必须与 docs/source 同步
node scripts/check-protocol-sync.mjs
```

> pre-commit 必须**快（< 10s）**，否则开发者会 `--no-verify` 绕过。只放秒级检查，不放全量测试。

#### L2：`.gitlab-ci.yml` + `.gitlab/CODEOWNERS`（暂不实施）

CI 配置见主方案 [§5.6](研发效能基线建设-技术方案.md)。CODEOWNERS 把「改错影响全系统」的文件保护人显式化：

/src/interceptor/                   @hhr
/src/service/alova.ts                @hhr
/docs/source/07-协议事件清单.md      @hhr
/herness/                            @hhr

### 3.4 文档同步自动化（P1）

herness 最大的同步风险是「文档与代码同步」纯靠自觉——SOP 写了「实现有偏差必须回写」，但无任何机制检查。三类可自动化的检查：

| 检查 | 实现方式 | 拦截什么 |
|------|---------|---------|
| **① 协议一致性** | 脚本解析 `src/const/const.message.type.ts` 的 `MESSAGE_EVENT_KEY`，与 `docs/source/07-协议事件清单.md` 比对 | 新增事件键忘同步文档 |
| **② 类型定义存在** | 断言 `MESSAGE_EVENT_KEY` 中不存在被引用但未定义的键（即现存 6 个 `TS2339/TS2551`） | 引用不存在的消息键 |
| **③ 文档时效性** | 比对关键文件 mtime 与 `当前状态摘要.md` 的日期字段 | 文档描述 stale |

① 的骨架：

```js
// scripts/check-protocol-sync.mjs
// 1. 解析 const.message.type.ts 中所有 MESSAGE_EVENT_KEY 的键名
// 2. 提取 docs/source/07-协议事件清单.md 中已登记的事件键
// 3. 差集 = 未同步的键；有则 exit 1 并列出
```

这个脚本把 SOP 里的**真实缺陷**（6 个 `TS2339/TS2551` 引用了不存在的键）从「靠人记得修」变成「机器持续拦截」。

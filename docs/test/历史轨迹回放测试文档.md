# 历史轨迹回放 · 测试文档

> 面向 QA 与前端联调，简洁明了。

---

## 一、功能简介

警情进入**终态**后，清空原有警情产物（队站/资源/路径），自动查询出动车辆轨迹并在地图上渲染回放面板。

### 触发条件

| 触发源 | 说明 |
|--------|------|
| WS 消息 `ALARM_INCIDENT/STATE_CHANGED` | 5 个终态均触发：`ARRIVED` / `OPERATION_COMPLETED` / `RETURNED` / `CLOSED` / `POST_ACTION_REVIEWED` |
| 共享态 `currentAlarm.lifecycleStage="closed"` | 受理席写入 lifecycleStage，前端 watcher 监听变化 → **独立触发历史轨迹回放**，不需要等终态 WS 到达 |

> 两条链路**平级独立、互不依赖、幂等**，可同时到达，终态标记只会触发一次。

### 数据流（两条平级入口汇合）

```
┌─ ALARM_INCIDENT/STATE_CHANGED（终态 WS）→ AlarmController ──┐
│                                                              ├→ markTerminal → beginVehicleTrack
└─ currentAlarm.lifecycleStage="closed"（共享态）→ onLifecycleStageChange ─┘
  → useDispatchEntangled（清空警情产物 → 查询出动车辆 → 逐车查询轨迹）
  → useVehicleTrackStore（存轨迹 + 标记终态）
  → VehicleTrackRenderer（多组并行渲染：全轨迹线 + 已走灰线 + 车辆图标 + 方向箭头）
  → VehicleTrackPanel（回放面板：时间轴 + 速度 + 路线切换 + 轨迹统计）
```

### 关键文件（前端）

| 文件 | 职责 |
|------|------|
| `src/apis/carTrack.ts` | 轨迹查询 API、车辆提取、路线分组 |
| `src/store/useVehicleTrackStore.ts` | 轨迹状态 + 终态标记（持久化 sessionStorage） |
| `src/composables/useVehicleTrackPlayback.ts` | 回放引擎（gpsTime 时间轴 + requestAnimationFrame） |
| `src/baseComponent/OpenlayersMap/VehicleTrackRenderer.ts` | OL 渲染器（多组并行、颜色分组） |
| `src/components/dispatchMap/VehicleTrackPanel.vue` | 回放面板 UI |
| `src/utils/trackStatistics.ts` | 轨迹统计（速度分布/停留点/异常） |
| `src/utils/incidentState.ts` | 终态判定（5 个终态集合） |

1. **填身份**：`userId` / `sessionState`（或直接粘贴 accessToken）
2. **写测试状态**：GIS 测试状态下拉选「调派」，填 `incidentId` → 点「写入测试状态」

5. **推送终态**：消息预设选「警情状态变更」→ 警情新状态选终态 → 推送当前 JSON

### 警情新状态速查

| 状态 | 是否终态 | 触发轨迹回放 |
|------|---------|-------------|
| `CREATED` 立案 | ✗ | ✗ |
| `DISPATCHED` 出动 | ✗ | ✗ |
| `ARRIVED` 到场 | ✓ | ✓ |
| `OPERATION_COMPLETED` 展开 | ✓ | ✓ |
| `RETURNING` 归队中 | ✗ | ✗（容易踩坑） |
| `RETURNED` 归队 | ✓ | ✓ |
| `CLOSED` 结案 | ✓ | ✓ |
| `POST_ACTION_REVIEWED` 战评 | ✓ | ✓ |

## 三、测试判定标准（必读，避免假 PASS）

### 3.1 投递 ≠ 功能生效

测试控制台显示 **PASS** 只代表 **WS 消息成功投递到前端客户端**（`matched=1` / `delivered=1`），**不代表历史轨迹回放真的触发了**。

前端有一道**状态门禁**（`messageStagePolicy`）：消息到达后，会检查当前前端 stage 是否匹配。`ALARM_INCIDENT/STATE_CHANGED` 要求 stage=`dispatch`（由 `phase=inquiry` + `currentAlarm` 非空推导）。**不匹配时消息被静默丢弃**，只在 console 打 `忽略状态不匹配的消息`，不报错、不重试。

所以会出现：**控制台 7 步全 PASS，但地图屏还停在警情调派阶段、轨迹面板根本没出现**。

### 3.2 PASS 的双重判定

每个用例 PASS 必须**同时满足**以下两项，缺一不可：

| 判定层 | 检查方式 | 说明 |
|--------|---------|------|
| ① 投递层 | 测试控制台 `matched=1`、`delivered=1` | 消息到达前端（必要不充分） |
| ② 功能层 | **肉眼观察地图屏** | 轨迹面板出现 / 警情产物清空 / HTTP 请求发出（充分必要） |

> 只有 ① 没有 ② = **假 PASS**，按"假 PASS 排查指南"（第七章）定位。

### 3.3 地图屏预期变化速查

触发历史轨迹后，地图屏**必须**同时出现以下变化（任一缺失即功能未生效）：

- 原有警情产物消失：路径规划面板（"接警处置台路线预览"）关闭、队站/资源标记清除、路径线清除
- 底部弹出「车辆历史轨迹回放」面板（含时间轴 / 倍速 / 路线切换 / 轨迹统计）
- 地图上出现轨迹线（完整线 + 已走灰线 + 车辆图标 + 方向箭头）

## 四、测试用例

> 以下所有用例的「预期」均遵循第三章双重判定：控制台投递指标 + 地图屏可见变化。**控制台 PASS 但地图屏无变化 = 假 PASS**，立即按第七章排查，不要继续往下跑。

### TC-TRK-01 CLOSED 结案触发历史轨迹

**等级**：P0

**前置**
- 已写入 dispatch 态（警情 ID 有效）
- GIS 地图已打开并连接
- 后端该警情能查到出动车辆 + 轨迹数据（贵州车辆）

**步骤**
1. 控制台「消息预设」= 警情状态变更，「警情新状态」= `CLOSED · 结案`
2. 核对 `incidentId` 与共享态一致 → 推送当前 JSON
3. 等待 6 秒

**预期**
1. 控制台 `matched=1`、`delivered=1`
2. 原有警情产物（队站/资源/路径）被清空
3. 地图出现轨迹：完整线 + 已走灰线 + 车辆图标 + 方向箭头
4. 底部弹出「车辆历史轨迹回放」面板

### TC-TRK-02 五个终态逐一触发（等价类）

**等级**：P1

**前置**：每轮用不同 incidentId，或切回值守后重进

**步骤**
1. 依次推送 `ARRIVED` → `OPERATION_COMPLETED` → `RETURNED` → `POST_ACTION_REVIEWED`（`CLOSED` 已覆盖）
2. 每次等 6 秒，检查是否进入轨迹链路

**预期**
1. 5 个终态全部触发，行为一致
2. `RETURNING · 归队中` **不**触发（对照项）
3. 同一警情重复推终态时 console 提示「沿用已有轨迹」

### TC-TRK-03 非终态不触发，换警情清空旧轨迹

**等级**：P2

**前置**：TC-TRK-01 通过，当前警情 A 有轨迹面板

**步骤**
1. 对 A 推送 `DISPATCHED · 出动` → 等 2 秒
2. 改 incidentId 为 B，写入 dispatch 态
3. 对 B 推送终态

**预期**
1. 步骤 1 不触发轨迹，A 的轨迹不变
2. 步骤 3 触发清空：A 的轨迹消失、面板关闭
3. B 正常加载自己的轨迹

### TC-TRK-03B 共享态兜底：currentAlarm.lifecycleStage="closed" 与 WS 终态平级触发

**等级**：P0（兜底链路，生产关键）

**场景**：前端有**两条平级触发链路**进入历史轨迹：
- WS 链路：`ALARM_INCIDENT/STATE_CHANGED` 终态消息 → `AlarmController`
- 共享态链路：受理席写入 `currentAlarm.lifecycleStage="closed"` → `useDispatchEntangled.onLifecycleStageChange`

两条链路**互不依赖、各自独立、幂等**。WS 丢失时共享态兜底，WS 到达时共享态可叠加，终态标记只会触发一次。

**前置**
- 已写入 dispatch 态（`phase=inquiry` + `currentAlarm.incidentId=xxx`）
- GIS 地图已打开并连接

**步骤**（两条路径任选其一或组合执行）

| 路径 | 操作 | 说明 |
|------|------|------|
| A. 仅共享态 | DevTools → Local Storage → `seat-shared-state`，在 `currentAlarm` 追加 `"lifecycleStage": "closed"` 并保存 | 不推任何 WS 终态消息，纯共享态触发 |
| B. 仅 WS | 控制台推送终态（如 `ARRIVED`） | 不写 lifecycleStage，纯 WS 触发 |
| C. 两链路叠加 | 先执行 A，再执行 B → 观察 console | 或先 B 后 A，两条路径顺序颠倒均可 |

```jsonc
// seat-shared-state 示例（路径 A / C）
"currentAlarm": { "incidentId": "你的 incidentId", "lifecycleStage": "closed" }
```

**预期**
1. 三条路径均能在 6 秒内触发轨迹面板，行为完全一致（清空警情产物 → HTTP 查车 → HTTP 查轨迹 → 面板出现）
2. 路径 C（两链路叠加）时，console 只出现一次终态标记日志，**无重复 HTTP 请求**（幂等）
3. 控制台 Console 搜索 `lifecycleStage` 可看到 watcher 触发日志（路径 A / C）
4. 搜索 `STATE_CHANGED` 可看到 WS 终态触发日志（路径 B / C）

**边界验证**
- 把 `lifecycleStage` 改回 `""` 或删除 → 面板消失、恢复警情产物（终态标记撤销）
- `lifecycleStage` 写 `"open"` / `"unknown"` → **不**触发（只有 `"closed"` 生效）
- 对同一警情，路径 A 触发后推送一条 `DISPATCHED`（非终态）→ 面板**不**消失（终态标记优先级高于非终态 WS）

## 七、假 PASS 排查指南（控制台 PASS 但地图屏无变化）

**现象**：测试控制台显示全部 PASS，但地图屏仍停在警情调派阶段（显示"接警处置台路线预览"、图层选择器、路径规划），历史轨迹面板未出现。

**根因**：消息投递成功 ≠ 前端处理成功。前端 `messageStagePolicy` 门禁不匹配时**静默丢弃**消息（只打 console 日志，不报错）。

按以下顺序排查（GIS 页面 DevTools）：

| 步骤 | 检查位置 | 找什么 | 结论 / 处置 |
|------|---------|--------|------------|
| 1 | Console 搜 `忽略状态不匹配` | 有无该日志 | 有 = 门禁丢消息，转步骤 2；无 = 消息未投递或已被处理，转步骤 3 |
| 2 | Application → Local Storage → `seat-shared-state` | `phase` + `currentAlarm` | 要求 `phase="inquiry"` 且 `currentAlarm.incidentId` 非空且与消息 incidentId 一致；不一致 → 修正共享态后重推 |
| 3 | Console 搜 `收到 ALARM_INCIDENT/STATE_CHANGED` | 日志里的 `incidentId` / `newState` | 无日志 = 消息没到前端（WS 未推到或门禁丢弃）；有日志但 newState 非终态 = 推错状态；incidentId 与共享态不一致 = 换警情串场 |
| 4 | Console 搜 `车辆历史轨迹` / `终态触发` | 有无触发日志 | 无 = `handleAlarmStateChanged` 未调用（门禁或订阅问题）；有 = 已进入轨迹链路，转步骤 5 |
| 5 | Network 面板 | `/bff-client/.../turnout-vehicles` 请求 | 无请求 = `beginVehicleTrack` 未触发；有请求但非 200 = BFF mock 未拦截，转步骤 6 |
| 6 | mock-ws.js 服务端终端日志 | `[BFF-MOCK]` 命中记录 | 无命中 = 请求未走 mock 代理（检查 Vite 代理 / 接口前缀）；有命中但返回空 = mock 数据 incidentId 不匹配 |

**常见修复**：
- 门禁丢消息：test-ui 跑场景时确认「模式同步」指示器显示 `gate=dispatch` 后再推终态；手动测试时先写 dispatch 态再推消息
- incidentId 串场：test-runner 每 run 生成独立 incidentId（`INC-xxxxxxxx`），不要在控制台手动覆盖共享态的 incidentId
- BFF mock 未命中：确认 mock-ws.js 已启动且拦截了 `/bff-client` 与 `/car-track-api` 前缀（见 `server/mock-ws.js` 的 `handleBffMock`）

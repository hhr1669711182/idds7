### 09-前端业务逻辑设计

> 版本: v1.0\
> 日期: 2026-07-24\
> 范围: GIS 前端运行时 — 业务控制层核心业务规则与决策链

***

## 0. 设计原则

GIS 前端的业务逻辑统一收敛在 **业务控制层**（Business Control Layer），按 6 个业务域进行划分：

| 业务域 | 控制器            | 核心规则数 |
| --- | -------------- | ----- |
| 警情  | `AlarmCtrl`    | 12    |
| 来电  | `CallCtrl`     | 6     |
| 问询  | `InquiryCtrl`  | 5     |
| 调派  | `DispatchCtrl` | 14    |
| 值守  | `DutyCtrl`     | 7     |
| 跟踪  | `TrackingCtrl` | 9     |

**强制规约**：

1. 所有业务规则必须在 **业务控制层** 实现，渲染层只做"展示 + 事件转发"，不允许出现 if/else 业务判断。
2. 通用规则（Auto-Fit、坐标系转换、视野控制）由 **通用控制层** 承载，业务控制层只负责装配"业务参数"（如 zoom=18 + 500m 圈）。
3. 关键业务判断（详见 [11-核心业务判断逻辑](./11-核心业务判断逻辑.md)）由 `decision` 函数统一封装，禁止散落在多个方法中。

***

## 1. 警情业务规则（AlarmCtrl）

### 1.1 警情订阅规则

- 警情订阅通道 `AlarmSyncEvent` 进入业务控制层时，**必须**先经过 `protocolLayer.deserialize()` 反序列化为标准 `AlarmProfile`（WGS84 坐标系）。
- 同一警情 ID 在前端仅保留最新版本，老版本通过 `OperationLog` 留痕。
- 订阅采用"按席位 + 按中心"双维度过滤，接警员仅可见本中心警情。

### 1.2 警情渲染规则

| 场景   | 缩放级别      | 视野     | 围栏                 | 触发指令             |
| ---- | --------- | ------ | ------------------ | ---------------- |
| 值守   | zoom = 15 | 全中心    | 无                  | `fitToDuty`      |
| 来电弹屏 | zoom ≥ 18 | 500m 圈 | 来电位置 500m 圆        | `locateToCall`   |
| 问询研判 | 17 \~ 19  | 微围栏    | 来电位置 100m 圆        | `focusOnInquiry` |
| 图上调派 | 16 \~ 19  | 四级围栏   | 1km/500m/200m/100m | `cascadeFit`     |
| 跟踪到场 | ≥ 19      | 微观视图   | 50m                | `zoomInTracking` |

### 1.3 警情 ID 隔离规则

- 所有警情图元 ID 必须加 `alarm_` 前缀（如 `alarm_marker_${alarmId}`）。
- 警情关闭时通过 `AlarmCtrl.release(alarmId)` 精准回收，**禁止**全量 `clearLayer`。

### 1.4 警情状态迁移规则

- 警情状态机严格遵循 [08-业务状态机定义](./08-业务状态机定义.md) 的迁移表。
- 警情关闭时必须联动调派计划状态机（详见 08 §4 跨状态机联动规则）。

***

## 2. 来电业务规则（CallCtrl）

### 2.1 来电弹屏规则

- 来电进入时，立即触发 `locateToCall`（zoom=18，500m 圈）。
- 同时启动 5s 倒计时（用于自动接听/拒接），超时未操作按业务规则执行。
- 同一时间最多弹屏 **3 路** 来电，第 4 路进入排队。

### 2.2 来电 ID 规则

- 来电图元 ID 前缀为 `call_`。
- 来电挂断后立即回收，不留缓存。

### 2.3 来电与警情关联规则

- 来电转警情时必须通过 `CallCtrl.relateToAlarm(callId, alarmId)` 建立绑定。
- 关联后的来电与警情共享视野焦点。

***

## 3. 问询业务规则（InquiryCtrl）

### 3.1 问询研判规则

- 问询开始时聚焦来电位置 100m 微围栏（zoom=17\~19）。
- 问询过程中实时高亮来电位置，确保接警员精准确认事发地。
- 问询过程中不得触发其他业务的视野变化（焦点独占）。

### 3.2 问询信息持久化规则

- 问询信息（地址、灾情类型、伤亡）写入 `CallLocation.payload` 字段，前端在提交派警时一并上传。
- 问询未提交时关闭弹窗，必须二次确认（防止误关丢失问询内容）。

***

## 4. 调派业务规则（DispatchCtrl）

### 4.1 调派四级围栏规则

| 围栏级别  | 距离   | 视觉    | 触发场景 |
| ----- | ---- | ----- | ---- |
| L1 一级 | 1km  | 淡蓝色虚线 | 全区概览 |
| L2 二级 | 500m | 浅蓝色实线 | 邻近分析 |
| L3 三级 | 200m | 中蓝色实线 | 调派范围 |
| L4 四级 | 100m | 深蓝色实线 | 精确到场 |

四级围栏联动：`fitToDispatch` 指令同时下发 4 个围栏，渲染层按 zoom 自动显示/隐藏。

### 4.2 算路规则

- 算路耗时 ≤ 1s（参考 [GIS 性能 SLA](file:///d:/work/telewave/ids/ids-gis-web/skills/20260717-培训材料-肖志威/gis-dev-workflow/references/gis-performance-sla.md)）。
- 算路结果通过 `MessageEnvelope<DispatchRoute>` 发布，**包含** WGS84 坐标串。
- 算路失败时降级为直线段并打点 `ROUTE_FALLBACK`。

### 4.3 调派 ID 规则

- 调派路径图元 ID 前缀为 `route_`。
- 调派计划 ID 前缀为 `plan_`。

### 4.4 调派车辆选择规则

- 可调派车辆必须在 `IN_GARAGE` 状态（详见 08 §2 车辆状态机）。
- 选择车辆时按"距离最近 + 状态最优"双因子排序，**禁止**按字母顺序或随机选车。

***

## 5. 值守业务规则（DutyCtrl）

### 5.1 值守视野规则

- 值守状态下默认 zoom = 15，覆盖全中心。
- 视野自适应需保留 10%\~15% Padding（详见 [GIS 坐标系规约](file:///d:/work/telewave/ids/ids-gis-web/skills/20260717-培训材料-肖志威/gis-dev-workflow/references/gis-coord-system.md)）。

### 5.2 值守图层规则

- 值守时仅加载基础底图 + 中心点标记，**不**加载警情/车辆/调派图层。
- 切换到警情/调派/跟踪场景时按需加载。

### 5.3 资源图层规则

- 兴趣面（`gis:env_build_aoi`）默认在 zoom ≥ 16 时显示。
- 出入口（`gis:env_entrance_exit`）在 zoom ≥ 17 时显示。
- 消防栓（`gis:env_fire_water`）在 zoom ≥ 18 时显示。
- 道路（`gis:env_greatchina_road`）按矢量瓦片自动分级。

***

## 6. 跟踪业务规则（TrackingCtrl）

### 6.1 车辆跟踪规则

- 车辆 GPS 推送频率 ≥ 2fps，订阅通道进入 Web Worker。
- Web Worker 负责坐标转换、距离计算、围栏命中判断，结果通过 `Transferable Objects` 回主线程。
- 主线程按 ≥ 30fps 频率刷新渲染，但状态机更新按"事件驱动"（围栏命中/状态变更才触发）。

### 6.2 跟踪视野规则

- 跟踪模式下 zoom ≥ 19，50m 微观视图。
- 镜头跟随绑定车辆（"哪辆车被选中就跟哪辆"），不允许多车同时抢焦点。 

### 6.3 跟踪 ID 规则

- 车辆图元 ID 前缀为 `vehicle_`。
- 车辆轨迹图元 ID 前缀为 `trail_`。
- 车辆离场（`CLOSED`）时通过 `TrackingCtrl.release(vehicleId)` 精准回收。

### 6.4 跟踪性能规则

- 单中心最大同时跟踪车辆数 ≤ 50，超过时进入"聚合渲染"模式（聚合为热力图）。

***

## 7. 跨业务域联动规则

### 7.1 业务域焦点互斥

- 同时只有一个业务域拥有"焦点控制权"（focus owner）。
- 焦点拥有者触发视野变化时，其他业务域的视野指令被丢弃。
- 焦点切换通过 `MessageEnvelope<FOCUS_CHANGE>` 广播。

### 7.2 业务域资源互斥

- 同一图元不能被多个业务域同时占用（如同一车辆不能同时被"调派"和"跟踪"两个域抢焦）。
- 抢占规则：先到先得；同帧内通过业务优先级（调派 > 跟踪 > 问询 > 来电 > 值守）裁决。

### 7.3 业务域退出规则

- 业务域退出（如关闭警情弹窗）必须发布 `DOMAIN_EXIT` 事件，由当前焦点拥有者主动释放。
- 强制退出（如警情关闭）由业务控制层调用 `release()` 接口释放资源。

***

## 8. 业务不变量保护

| 不变量        | 强制要求                        | 违反响应                        |
| ---------- | --------------------------- | --------------------------- |
| 坐标系        | 协议层/服务层强约束 WGS84，转换仅由底座插件负责 | 阻断渲染并打点 `COORD_VIOLATION`   |
| 视野 Padding | Auto-Fit 必须保留 10%\~15% 留边   | 自动修正并打点 `PADDING_AUTO_FIX`  |
| 业务 ID 前缀   | 所有图元 ID 加业务前缀               | 阻断发布并打点 `ID_PREFIX_MISSING` |
| 状态机迁移      | 严格按 08 定义的有向边迁移             | 阻断并打点 `ILLEGAL_TRANSITION`  |
| 业务焦点互斥     | 同时仅一个业务域拥有焦点                | 丢弃后到指令并打点 `FOCUS_CONFLICT`  |

***

## 9. 人工操作触发链

接警员/值班长通过 UI 触发业务动作时，统一走以下处理链：

```
UI 事件 → 业务控制层 (AlarmCtrl/CallCtrl/...)
    ↓
protectInvariants() 不变量保护
    ↓
decision() 业务判断
    ↓
stateMachine.transit() 状态机迁移
    ↓
protocolLayer.publish(MessageEnvelope<T>) 协议发布
    ↓
通用控制层 (GeometryCtrl/ViewCtrl/...) 执行
    ↓
渲染层 (OpenLayers/ThreeJS) 绘制
    ↓
OperationLog 留痕 + GIS_OPERATION 打点
```

**强制约束**：

- 任何业务动作必须经过完整链路，**禁止** UI 直接调用通用控制层。
- 通用控制层只接收 **通用控制层输入指令集（Generic Control Input DTOs）**，不感知业务参数。

## 10. 异常处理对齐

业务规则的异常处理详见 [12-异常处理流程](./12-异常处理流程.md)，本文件不重复。

***

#### 断言清单

1. 所有业务规则必须收敛在业务控制层（6 个业务控制器），渲染层不允许出现 if/else 业务判断。
2. 5 个核心场景的视野规则（值守 15 / 来电 18+500m / 问询微围栏 / 调派四级围栏 / 跟踪 19+50m）由业务控制层负责装配，业务参数不下沉到通用控制层。
3. 业务域之间焦点互斥、资源互斥；同帧内按"调派 > 跟踪 > 问询 > 来电 > 值守"优先级裁决。
4. 所有图元 ID 加业务前缀（`alarm_` / `call_` / `route_` / `plan_` / `vehicle_` / `trail_`），关闭/离场时通过 `release(id)` 精准回收。
5. 人工操作必须经过 `protectInvariants → decision → stateMachine.transit → protocolLayer.publish → 通用控制层执行` 完整链路，UI 不得直接调用通用控制层。

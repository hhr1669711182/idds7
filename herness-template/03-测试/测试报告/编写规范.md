# 测试报告编写规范

> 本文档定义迭代测试报告的标准格式、章节结构、数据规范和质量要求。所有测试报告文档必须遵循本规范。

---

## 1. 文档结构规范

每份测试报告按以下固定章节组织：

```
# {项目/平台名称}-{模块名称}-测试报告           ← 或 {迭代编号}-{模块}-测试报告

## 1. 测试基本信息
## 2. 测试资源与环境
## 3. 缺陷统计与分析
## 4. 测试通过标准
## 5. 测试结论
```

---

## 2. 各章节编写规范

### 2.1 测试基本信息（§1）

**必填内容：**

| 项 | 说明 |
|----|------|
| 测试概述 | 1-2 段话说明测试策略（功能测试/性能测试/安全测试等）、测试目标、测试范围 |
| 测试范围表 | 按平台/端列出所有被测模块及测试结果 |

**测试范围表模板：**

```markdown
### {平台/端名称}

| 序号 | 功能模块 | 用例数 | 通过 | 失败 | 阻塞 | 测试结果 |
|------|---------|--------|------|------|------|---------|
| 1 | {模块名} | N | N | 0 | 0 | 测试通过 |
| 2 | {模块名} | N | N | 0 | 0 | 测试通过 |
| ... | ... | ... | ... | ... | ... | ... |
```

**测试结果取值：** `测试通过` | `测试不通过` | `部分通过` | `未测试` | `阻塞`

### 2.2 测试资源与环境（§2）

**必填内容：**

| 项 | 说明 |
|----|------|
| 测试环境 | 环境名称（如：测试环境、本地开发环境、预发布环境） |
| 测试链接 | 各平台/端的访问 URL |
| 测试账号 | 各角色测试账号及密码 |
| 硬件配置 | 测试所用电脑型号、操作系统 |
| 浏览器/客户端 | 浏览器名称及版本、App 版本 |
| 测试时间 | 测试起止日期 |
| 测试人员 | 测试执行人 |

**模板：**

```markdown
### {平台/端名称}

| 项目 | 内容 |
|------|------|
| 测试环境 | {环境名称} |
| 测试链接 | {URL} |
| 测试账号 | {账号} |
| 账号密码 | {密码} |
| 电脑配置 | {型号} / {操作系统} |
| 浏览器 | {浏览器及版本} |
| 测试时间 | YYYY/MM/DD 至 YYYY/MM/DD |
| 测试人员 | {姓名} |
```

### 2.3 缺陷统计与分析（§3）

**必填内容：**

| 项 | 说明 |
|----|------|
| 缺陷统计表 | 按严重等级汇总缺陷数量 |
| 缺陷分布说明 | 简述缺陷集中的模块或类型（可选） |

**缺陷统计表模板：**

```markdown
| 项目 | 致命 | 严重 | 一般 | 提示 | 建议 | 合计 |
|------|------|------|------|------|------|------|
| 有效缺陷数 | N | N | N | N | N | N |
| 比率 | X% | X% | X% | X% | X% | 100% |
| 已修复 | N | N | N | N | N | N |
| 遗留 | N | N | N | N | N | N |
```

**缺陷严重等级定义：**

| 等级 | 定义 | 判定标准 |
|------|------|---------|
| **致命** | 影响测试继续进行 | 关键功能错误、程序崩溃、非法退出 |
| **严重** | 功能不正确，影响系统运行 | 核心业务流程中断、数据错误，但不阻塞继续测试 |
| **一般** | 不影响运行但须修改 | 非核心功能缺陷、边界场景错误，部分可经项目讨论延期 |
| **提示** | 轻微问题 | 界面展示不美观、文案错别字 |
| **建议** | 优化建议 | 体验优化、功能增强建议 |

### 2.4 测试通过标准（§4）

**必填内容：**

1. **测试通过条件**（满足以下全部）：
   - 测试用例 / 测试需求执行率达 **100%**
   - 所有**致命**和**严重**缺陷均已修复并验证通过
   - 遗留的**一般/提示/建议**缺陷经项目小组讨论通过，确定不予修改或延后解决

2. **缺陷严重等级说明**（见 §2.3 等级定义表）

### 2.5 测试结论（§5）

**必填内容：**

- 一句话总结：是否按测试用例完成测试
- 缺陷总数与修复状态
- 最终判定：**测试通过** / **测试不通过** / **有条件通过**

**模板：**

```markdown
{平台/模块名称}功能测试已经按照测试用例完成测试，共发现 {N} 个有效缺陷，
其中致命 {N} 个、严重 {N} 个、一般 {N} 个。
全部致命/严重缺陷已修复并验证通过，
遗留一般缺陷 {N} 个（经项目讨论同意延期处理）。
综合评估，**测试{通过/不通过}**。
```

## 3. 命名规范

### 3.1 文件命名

```
{迭代编号}-{模块名称}-测试报告.md
```

**规则：**
- 迭代编号格式：`YYYY-WXX`
- 模块名称与测试用例文档中的模块名称一致
- 示例：`{YYYY-WXX}-{模块名}-测试报告.md`

### 3.2 报告标题

```
# {迭代编号} {模块名称} — 测试报告
```

---

## 4. 数据规范

### 4.1 用例数

- 报告中引用的用例数必须与对应的测试用例文档（`03-测试/测试用例/{模块}-测试用例.md`）中的合计值一致
- 用例数变动时，报告必须同步更新

### 4.2 缺陷数

- 缺陷统计以缺陷管理工具中的记录为准
- 缺陷状态（已修复/遗留）必须与工具中一致
- 缺陷数与用例的关联通过"缺陷回归用例"章节体现（如有）

### 4.3 时间

- 日期格式统一为 `YYYY/MM/DD`

### 4.4 缺陷-用例标注规则

> **核心原则**：测试报告中每条用例的执行结果，由已知缺陷驱动判定——命中缺陷的标注 FAIL 并关联 Bug，未命中的标注 PASS。

**标注流程：**

```
Step 1: 获取缺陷清单
  └→ 从缺陷管理工具导出当前模块的全部缺陷

Step 2: 缺陷 → 用例匹配
  └→ 逐条缺陷分析"如果执行这条用例，能否发现该缺陷"
  └→ 能发现 → 该用例标注为 FAIL，备注关联 Bug 编号和失败原因
  └→ 不能发现 → 检查该缺陷是否已有用例覆盖（若无 → 用例缺失，需补充）

Step 3: 标注测试用例文件
  └→ 在测试用例文档末尾新增「§10 测试执行记录」章节
  └→ 包含：执行结果总览（PASS/FAIL/BLOCKED 统计）
  └→ 包含：失败用例明细表（用例编号 + 关联 Bug + 失败原因）
  └→ 包含：分类通过率统计

Step 4: 输出测试报告
  └→ 将标注结果写入测试报告 §1（测试结果列）和 §3（缺陷-用例关联）
  └→ 已解决缺陷对应的用例标注 PASS（回归通过）
  └→ 待修复缺陷对应的用例标注 FAIL
  └→ 与任何缺陷无关的用例全部标注 PASS
```

**标注规则表：**

| 场景 | 用例结果 | 标注方式 |
|------|---------|---------|
| 用例命中**待修复**缺陷 | **FAIL** | 备注 `关联 Bug #N` + 失败原因 |
| 用例命中**已解决**缺陷 | **PASS** | 备注 `关联 Bug #N（已解决），回归通过` |
| 用例**未命中**任何缺陷 | **PASS** | 无需额外备注 |
| 缺陷**无对应用例** | — | 先补充用例，再按"待修复"标注 |

**测试用例执行记录模板（追加到测试用例文档末尾）：**

```markdown
## 10. 测试执行记录

> 执行时间：YYYY/MM/DD | 执行人：{姓名} | 环境：{环境名称}
> 关联缺陷：{缺陷清单链接}（N 条：X 已解决 / Y 待修复）

### 10.1 执行结果总览

| 结果 | 数量 | 占比 |
|------|------|------|
| **PASS** | N | X% |
| **FAIL** | N | X% |
| BLOCKED | N | X% |
| **合计** | **N** | 100% |

### 10.2 失败用例明细（对应缺陷）

| # | 用例名称 | 结果 | 关联 Bug | Bug 状态 | 失败原因 |
|---|---------|------|---------|---------|---------|
| N | {用例名} | **FAIL** | #N | 新 | {根因} |

### 10.3 已解决缺陷回归通过（PASS）

| # | 用例名称 | 关联 Bug | Bug 状态 | 验证结果 |
|---|---------|---------|---------|---------|
| N | {用例名} | #N | 已解决 | PASS — {验证说明} |

### 10.4 通过用例统计（按分类）

| 分类 | 总数 | PASS | FAIL | 通过率 |
|------|------|------|------|--------|
| {分类名} | N | N | N | X% |
| **合计** | **N** | **N** | **N** | **X%** |
```

**强制要求：**

1. 测试报告中的**每条用例执行结果**必须与测试用例文档 §10 中的标注一致
2. 缺陷-用例匹配结果必须写入测试用例文档（留痕），不可只存在于报告中
3. 若发现"缺陷无对应用例"，**必须先补充用例再标注**（参照 [测试用例编写规范 §8](../测试用例/编写规范.md)）
4. 标注完成后，测试报告的 §1 测试范围表必须填入实际 PASS/FAIL 数字，§3 必须包含"失败用例与缺陷关联"表

---

## 5. 报告类型

| 类型 | 用途 | 时机 |
|------|------|------|
| **功能测试报告** | 迭代测试执行完成后，汇总全量测试结果 | 迭代结束 |
| **缺陷回归测试报告** | 针对特定缺陷清单做用例匹配 + 回归验证 | 缺陷修复后 |
| **专项测试报告** | 性能测试、安全测试、兼容性测试等 | 专项完成 |

---

## 6. 审核清单

提交测试报告前，逐项自检：

- [ ] **结构完整**：5 个章节（基本信息、资源环境、缺陷统计、通过标准、结论）全部存在
- [ ] **用例数准确**：与对应测试用例文档合计值一致
- [ ] **缺陷数准确**：与缺陷管理工具一致
- [ ] **测试环境信息完整**：URL、账号、浏览器版本均已填写
- [ ] **测试结果明确**：每个模块标注了明确的测试结果（通过/不通过/阻塞）
- [ ] **缺陷统计表完整**：致命/严重/一般/提示/建议 五类均已统计
- [ ] **通过标准已引用**：§4 中明确列出测试通过条件
- [ ] **结论不模糊**：§5 中有明确的"测试通过"或"测试不通过"判定
- [ ] **关联文档已链接**：报告中引用了对应的测试策略、测试用例文档链接
- [ ] **命名规范**：文件名和标题符合 §3 规范
- [ ] **缺陷-用例已标注**：已按 §4.4 规则完成缺陷→用例匹配，测试用例文档 §10 已写入执行记录，报告 §1/§3 数据与之一致

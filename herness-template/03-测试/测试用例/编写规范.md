# 测试用例编写规范

> 本文档定义测试用例的标准格式、命名规范、优先级体系和质量要求。所有测试用例文档必须遵循本规范。

---

## 0. 编写依据

> **测试用例不是凭空想象出来的，必须从设计文档中提取测试场景。**

每份测试用例文档的编写，必须基于以下两份上游文档：

```
产品设计文档（PRD）              技术设计文档
      │                              │
      │  定义"做什么"                │  定义"怎么做"
      │  · 业务流程                  │  · API 接口契约
      │  · 页面交互                  │  · 数据模型 / 字段约束
      │  · 角色权限                  │  · 异常处理 / 错误码
      │  · 校验规则                  │  · 数据库变更
      │                              │
      ▼                              ▼
      └──────────┬───────────────────┘
                 │
                 ▼
          测试用例文档
          · 从 PRD 提取：正常流程、页面交互、权限控制
          · 从技术方案提取：接口参数边界、异常路径、数据一致性
```

| 依据文档 | 提供什么 | 测试用例从中提取什么 |
|---------|---------|-------------------|
| **产品设计文档**（`01-产品设计/`） | 业务流程、页面交互、角色权限、校验规则 | 功能测试用例（Happy Path、页面表单校验）、权限与安全用例（角色可见性）、集成测试链路 |
| **技术设计文档**（`02-技术设计/`） | API 接口契约、数据模型、字段约束、异常处理、错误码 | 边界与异常用例（参数边界、DB 故障）、接口测试用例（请求/响应格式）、数据一致性验证 |

**强制要求：**

1. 编写测试用例前，**必须先阅读**对应的产品设计文档和技术设计文档
2. 测试用例文档的 §1 文档信息中**必须链接**到这两份上游文档
3. 测试用例中的**字段名、接口路径、错误提示文案**必须与设计文档中的定义一致
4. 如果上游文档尚未完成，测试用例**不得开始编写**（遵循 SOP 质量门禁）

### 0.1 从产品设计提取用户使用场景

> 功能测试用例验证"按钮能不能用"，场景测试用例验证"用户能不能完成一件事"。
> 编写测试用例的第一步，是从产品设计文档中梳理出**完整的用户使用场景**。

**提取步骤：**

```
Step 1: 识别角色
  └→ 从 PRD 中列出所有涉及的用户角色

Step 2: 识别目标
  └→ 每个角色使用该功能要达成的目标是什么？

Step 3: 绘制旅程
  └→ 角色从哪个入口进入 → 经过哪些页面/操作 → 最终达成什么结果

Step 4: 列出发量化验证点
  └→ 旅程中每个关键节点，用户"看到了什么""系统记录了什么"
```

**场景描述模板：**

每个场景按以下格式记录，作为后续场景测试用例的输入：

```markdown
### 场景 {N}：{场景名称}

| 属性 | 值 |
|------|-----|
| 场景ID | SCEN-{MODULE}-{NNN} |
| 角色 | {谁在使用} |
| 目标 | {要达成什么} |
| 前置状态 | {系统当前状态、已有数据} |
| 触发事件 | {用户做了什么操作启动该流程} |

**旅程步骤：**

| # | 操作 | 页面/入口 | 系统响应 | 数据变更 |
|---|------|----------|---------|---------|
| 1 | {用户动作} | {所在页面} | {页面反馈} | {后端数据变化} |
| 2 | ... | ... | ... | ... |

**结束状态：** {流程完成后的系统状态、数据状态}
```

**场景提取原则：**

| 原则 | 说明 |
|------|------|
| 一个场景 = 一个完整的用户目标 | 不把半个流程当成一个场景 |
| 覆盖所有角色 | 每个角色至少 1 个场景（含无权限角色的拒绝场景） |
| 覆盖核心路径 + 替代路径 | Happy Path（正常完成）+ Alternative Path（中断/回退/异常退出） |
| 明确数据变更 | 每个步骤标注后端数据变化（INSERT/UPDATE/DELETE），用于后续数据库级验证 |

> **场景提取完成后**，将用户使用场景写入测试用例文档的 §3「用户使用场景」章节，
> 再基于每个场景拆解出 §4~§8 的详细测试用例。

### 0.2 跨模块功能影响分析

> **一个功能往往不只存在于一个模块中。** 校验功能 A 时，不能仅在 A 模块内部编写测试用例，还需要识别所有涉及 A 功能的其他模块，并为每个关联模块输出对应的测试用例。

**核心原则：**

```
校验功能 A
    │
    ├── ① A 模块自身的测试用例（直接测试）
    │       └→ 功能入口、页面交互、API 调用、数据变更
    │
    └── ② 涉及 A 功能的其他模块的测试用例（间接测试 / 涟漪测试）
            └→ A 的数据被哪些模块读取？
            └→ A 的状态变更影响哪些模块的行为？
            └→ A 的操作结果在哪些模块中展示？
```

**分析步骤：**

```
Step 1: 识别 A 功能的"数据出口"
  └→ A 功能会产生/修改哪些数据？（表、字段、缓存、消息队列）
  └→ 这些数据被哪些模块消费？（查询、展示、统计、下游流程）

Step 2: 识别 A 功能的"行为出口"
  └→ A 功能的状态变更会触发哪些其他模块的行为？

Step 3: 识别 A 功能的"入口来源"
  └→ 哪些其他模块的操作会间接触发 A 功能？

Step 4: 列出跨模块影响矩阵
  └→ 用表格列出：关联模块、关联方式（读数据/触发行为/展示结果）、影响方向（A→模块 / 模块→A）

Step 5: 为每个关联模块编写测试用例
  └→ 每个关联模块至少 1 条验证用例，覆盖"数据是否正确传递""行为是否正确触发""展示是否正确"
```

**跨模块影响矩阵模板：**

```markdown
### 功能 {A} 的跨模块影响矩阵

| 关联模块 | 关联方式 | 影响方向 | 验证要点 | 对应测试用例编号 |
|---------|---------|---------|---------|---------------|
| {模块B} | 读取 A 产生的数据 | A → B | B 展示的 A 数据是否一致 | INTG-XXX |
| {模块C} | A 状态变更触发 C 行为 | A → C | C 的行为是否正确触发 | INTG-XXX |
| {模块D} | D 操作间接触发 A | D → A | D 操作后 A 是否正确响应 | INTG-XXX |
```

**关联方式分类：**

| 关联方式 | 说明 | 示例 |
|---------|------|------|
| **数据读取** | 其他模块读取/展示 A 功能产生的数据 | 费用中心展示充值的余额 |
| **状态联动** | A 的状态变更触发其他模块的行为变化 | 余额归零 → 创建工单时提示余额不足 |
| **流程串联** | A 是某个跨模块业务流程中的一环 | 认证 → 发布 → 充值 → 工单 → 激活 |
| **入口共用** | 多个模块共用同一页面/组件/菜单 | 多个入口共用企业搜索组件 |
| **数据写回** | 其他模块的操作会修改 A 依赖的数据 | 企业信息变更 → 记录中名称需同步更新 |

**强制要求：**

1. 编写测试用例前，**必须完成**跨模块影响矩阵（写入测试用例文档 §1 文档信息之后或 §3 用户使用场景之后）
2. 矩阵中**每个关联模块至少对应 1 条**测试用例（通常归入 §7 集成测试 或 §4 功能测试）
3. 如果矩阵为空（功能 A 确实不涉及其他模块），**必须明确说明原因**
4. 跨模块测试用例的期望结果中，**必须包含数据一致性校验点**

> **编写测试用例时，始终牢记：一个功能 = 自身模块的用例 + 所有关联模块的涟漪用例。** 缺少后者将导致集成阶段发现本应暴露的问题。

## 1. 文档结构规范

每份测试用例文档按以下固定章节组织：

```
# 测试用例 — {模块名称}

> 本文档遵循 03-测试/测试用例/编写规范.md

## 1. 文档信息
## 2. 用例概览
## 3. 用户使用场景        ← 从 PRD 提取，先场景后用例
## 4. 功能测试用例
## 5. 边界与异常测试用例
## 6. 权限与安全测试用例
## 7. 集成测试用例
## 8. 回归测试用例
```

### 1.1 文档信息

| 项 | 必填 | 说明 |
|----|------|------|
| 模块 | ✅ | 功能模块名称 |
| 关联迭代 | ✅ | 对应的迭代编号，如 {YYYY-WXX} |
| 关联产品设计 | ✅ | 链接到对应的 PRD 文档（`01-产品设计/` 下的文档） |
| 关联技术方案 | ✅ | 链接到对应的技术方案文档（`02-技术设计/` 下的文档，若有前后端分离则各链接一份） |
| 涉及页面 | 若有 | 列出涉及的前端页面名称 |
| 涉及接口 | 若有 | 列出涉及的后端 API 路径 |

### 1.2 用例概览

以表格汇总各类用例数量，示例：

| 分类 | 用例数 |
|------|--------|
| 用户使用场景 | N |
| 场景测试用例（从场景拆解） | N |
| 功能测试 — {子模块1} | N |
| 功能测试 — {子模块2} | N |
| 边界与异常 | N |
| 权限与安全 | N |
| 集成测试 | N |
| 回归测试 | N |
| **合计** | **N** |

## 2. 命名规范

### 2.1 文件命名

```
{模块名称}-测试用例.md
```

**规则：**
- 使用中文模块名，与产品需求文档保持一致
- 文件名不含特殊字符（`/` `\` `:` `*` `?` `<` `>` `|`）
- 示例：`{模块名}-测试用例.md`

### 2.2 用例编号规范

```
{CATEGORY}-{SUB}-{NNN}
```

**分类前缀：**

| 前缀 | 含义 | 来源 |
|------|------|------|
| `SCEN` | 用户使用场景（从 PRD 提取的完整旅程） | §0.1 场景提取 |
| `FUNC` | 功能测试用例 | §5.1 |
| `EDGE` | 边界与异常测试用例 | §5.2 |
| `AUTH` | 权限与安全测试用例 | §5.3 |
| `INTG` | 集成测试用例 | §5.4 |
| `REGR` | 回归测试用例 | §5.5 |

**示例：** `SCEN-AD-001`（场景-新增-第1条）、`FUNC-AD-001`（功能-新增-第1条）、`EDGE-001`（边界-第1条）

### 2.3 用例名称

```
{动作/场景} — {具体描述}
```

- 名称必须以动词或名词场景开头
- 用 `—`（全角破折号）分隔分类和描述
- 简洁明确，不超过 30 字
- ✅ 正确：`充值数量 — 输入 0`、`非账务角色不可见入口`
- ❌ 错误：`测试充值数量的边界情况`、`检查一下权限`

## 3. 优先级定义

| 优先级 | 含义 | 判定标准 | 执行要求 |
|--------|------|---------|---------|
| **P0** | 核心功能 | 不可绕过的主流程，任何缺陷都导致功能不可用 | 每次迭代必须全部通过 |
| **P1** | 重要功能 | 常规使用场景，影响用户体验但不阻塞核心流程 | 必须全部通过，可延后至迭代中期执行 |
| **P2** | 辅助功能 | 边缘场景、UI 细节、非关键体验优化 | 建议通过，可延后至迭代末期或下个迭代 |

**判断方法（按以下问题自问）：**

1. 此用例失败 → 用户能否完成核心任务？不能 → **P0**
2. 此用例失败 → 用户能否通过其他方式绕过去？能绕但体验差 → **P1**
3. 此用例失败 → 用户几乎不会注意到？是 → **P2**

**分布建议：**

| 优先级 | 建议占比 |
|--------|---------|
| P0 | 30%~40% |
| P1 | 40%~50% |
| P2 | 10%~20% |

## 4. 字段编写规范

每个测试用例包含以下 5 个必填字段 + 1 个可选字段：

| 字段 | 必填 | 说明 |
|------|------|------|
| `#` | ✅ | 用例序号，全局唯一递增 |
| `用例名称` | ✅ | 见 §2.3 |
| `前置条件` | ✅ | 测试执行前必须满足的条件 |
| `步骤` | ✅ | 具体的操作步骤 |
| `期望结果` | ✅ | 明确的验证点 |
| `优先级` | ✅ | P0 / P1 / P2 |

### 4.1 前置条件

**编写规则：**
- 以"已"开头描述已完成的状态
- 每个条件单独成句，用逗号分隔
- 不包含操作步骤（操作步骤写到"步骤"字段）

**示例：**

| ❌ 错误 | ✅ 正确 |
|--------|--------|
| 登录系统 → 进入直充 → 点新增 | 已登录运营（账务），进入直充页面 |
| 有数据 | 已存在 3 条不同企业的直充记录 |
| 填好表单 | 表单已填写企业、产品、数量，金额为空 |

### 4.2 步骤

**编写规则：**
- 动词开头（点击、输入、选择、查看、上传、打开）
- 步骤对应用户的一个操作或系统的一个响应
- 多步骤用编号（1. 2. 3.）分隔
- 精确到可复现的粒度（不要写"操作一下"）

**步骤粒度示例：**

| ❌ 太粗糙 | ✅ 正确粒度 |
|----------|-----------|
| 完成直充 | 点击「新增直充」→ 选择企业A → 选择产品X → 输入数量100 → 输入金额5000 → 上传凭证 → 点击「确认充值」→ 二次弹窗确认 |
| 查看列表 | 进入直充页面，查看表格各列 |

**关键原则：** 一个操作对应一个步骤，其他人照着步骤能 100% 复现。

### 4.3 期望结果

**编写规则：**
- 明确的、可验证的状态描述
- 每个期望结果必须有**可观测的判定标准**（看到什么、返回什么、提示什么）
- 用数值、文案、元素精准描述，禁止模糊词

**禁用词（不可出现在期望结果中）：**

| 禁用词 | 替换为 |
|--------|--------|
| 正确展示 | 展示"{具体文案}" / 字段"A"值为"B" |
| 功能正常 | 页面正常加载，{具体元素}可见且可交互 |
| 大概/可能 | 删除这些不确定词 |
| 没有异常 | 无错误提示 / 无 500 错误 / 页面不闪退 |

**示例：**

| ❌ 模糊 | ✅ 明确 |
|--------|--------|
| 充值成功 | 抽屉关闭，列表自动刷新，新增记录排列在列表第 1 行（创建时间倒序），顶部提示"充值成功"（3 秒后自动消失） |
| 按钮灰色不可用 | 按钮置灰（`disabled`），hover 显示 tooltip "该企业暂无可用产品"，点击无响应 |
| 列表正常 | 表格展示 5 列：记录ID、企业名称、产品名称、充值数量、充值时间；按充值时间倒序排列 |

## 5. 测试用例分类标准

### 5.0 场景测试用例（基于用户使用场景）

> 场景测试用例是功能测试用例的**上层编排**。它不孤立地验证单个按钮或接口，而是验证一个真实用户从"产生意图"到"达成目标"的完整路径。

**与功能测试用例的区别：**

| 维度 | 场景测试用例 | 功能测试用例 |
|------|-----------|------------|
| 粒度 | 用户目标级（横跨多页面/多接口） | 功能点级（单页面/单接口） |
| 来源 | PRD 中的用户旅程 | PRD + 技术方案中的字段/校验/交互定义 |
| 覆盖范围 | 端到端，跨越多个系统/页面 | 单点，聚焦一个功能或一个校验规则 |
| 关注点 | 用户能否**完成一件事** | 按钮/接口**行为是否正确** |
| 复现性 | 需按用户真实操作顺序执行 | 可独立执行 |
| 编号前缀 | `SCEN` | `FUNC` |

**场景测试用例编写流程：**

```
Step 1: 读取 PRD
  └→ 识别角色、目标、旅程步骤（见 §0.1 场景提取模板）

Step 2: 将场景填入测试用例文档 §3「用户使用场景」
  └→ 每个场景含：场景ID、角色、目标、前置状态、旅程步骤表、结束状态

Step 3: 从场景的每个旅程步骤拆解出功能测试用例
  └→ 场景步骤 → 功能测试用例（§4），用 FUNC-XXX 编号

Step 4: 补充场景级别的验证
  └→ 完整流程的执行 + 跨步骤的数据一致性校验
```

**场景测试用例编写标准：**

| 字段 | 编写要求 |
|------|---------|
| 用例名称 | `{场景名} — 完整链路` |
| 前置条件 | 描述场景的完整起始状态（角色、数据、系统状态） |
| 步骤 | 严格按场景旅程步骤顺序列出，不可跳过中间步骤 |
| 期望结果 | 覆盖每个步骤的校验点 + **跨步骤数据一致性**（如：操作前的余额 → 操作后的余额） |
| 优先级 | 场景级用例一般为 **P0**（核心用户目标） |

**场景覆盖要求：**

| 场景类型 | 最低数量 | 说明 |
|---------|---------|------|
| 主角色 Happy Path | 每个角色 1+ | 该角色使用本功能的核心完整路径 |
| 替代路径 | 1+ | 中断操作（关闭抽屉/取消弹窗/中途退出）后的状态 |
| 多角色协作链路 | 1+ | 涉及 2 个及以上角色先后操作的完整流程 |
| 拒绝/失败场景 | 1+ | 角色因权限/状态不满足而无法完成目标的完整路径 |

### 5.1 功能测试用例

覆盖业务主流程的正向和负向验证。按**页面/API/子功能**拆分子章节。

**包含内容：**
- 正常流程（Happy Path）
- 表单校验（必填项、格式校验、范围校验）
- 列表展示与筛选
- 按钮/操作的状态变化
- 各操作入口的可达性

**组织方式：**

```markdown
### 3.1 {子功能名称}（{编号前缀}, PAGE-{页码}）

| # | 用例名称 | 前置条件 | 步骤 | 期望结果 | 优先级 |
|---|---------|---------|------|---------|--------|
```

### 5.2 边界与异常测试用例

覆盖输入边界、异常数据和故障场景。

**必须覆盖的维度：**

| 维度 | 示例 |
|------|------|
| 数值边界 | 最小值-1、最小值、最大值、最大值+1、0、负数 |
| 字符串边界 | 空字符串、超长字符串、特殊字符、空格 |
| 列表边界 | 空列表、单条记录、分页边界 |
| 并发冲突 | 短时间重复操作、同数据并发修改 |
| 数据状态异常 | 关联数据已删除/已隐藏/已过期 |
| 零跨度范围 | 时间范围开始=结束（单日查询）、数量=1（单条边界）、分页第1页=最后一页 |
| 中间态/草稿态 | 对象仅保存未提交（名称/字段可能为空）、审核中、处理中 |
| 网络异常 | 请求超时、服务不可用 |

### 5.3 权限与安全测试用例

覆盖角色权限和数据隔离。

**必须覆盖的维度：**

| 维度 | 示例 |
|------|------|
| 角色权限 | 不同角色是否仅可见有权限的功能入口 |
| URL 越权 | 直接访问无权限 URL 是否被拦截 |
| 数据隔离 | 企业 A 是否无法访问企业 B 的数据 |
| 参数篡改 | 修改请求参数中的 ID 是否返回无权限 |

### 5.4 集成测试用例

覆盖端到端的多系统/多步骤联动场景。

**要求：**
- 至少覆盖 1 条完整业务闭环链路
- 至少覆盖 1 条多角色协作场景
- 涉及消息队列时，包含异步消息验证

### 5.5 回归测试用例

覆盖本次改动可能影响的已有功能。

**选择标准：**
- 与本次改动模块有**数据交互**的功能
- 与本次改动模块**共用组件/接口**的功能
- 与本次改动模块在**同一页面/菜单**下的相邻功能

## 7. 审核清单

提交测试用例文档前，逐项自检：

- [ ] **上游文档已读**：已阅读关联的产品设计文档和技术设计文档
- [ ] **文档链接必填**：§1 文档信息中「关联产品设计」和「关联技术方案」均已填写有效链接
- [ ] **场景先于用例**：§3「用户使用场景」已从 PRD 中提取完成（每个角色 ≥1 场景），场景覆盖了 Happy Path + 替代路径 + 失败路径
- [ ] **场景已拆解**：每个用户使用场景已对应至少 1 条场景测试用例（SCEN 编号）
- [ ] **结构完整**：8 个章节（文档信息、概览、用户使用场景、功能、边界、权限、集成、回归）全部存在
- [ ] **编号连续**：用例 # 从 1 开始，连续无跳号
- [ ] **概览准确**：用例概览表中的数字与实际条数一致
- [ ] **覆盖全面**：每个功能的正常 + 边界 + 异常 + 权限场景均已覆盖
- [ ] **前置条件到位**：每条用例的前置条件不包含操作步骤
- [ ] **步骤可复现**：非原作者能照着步骤独立执行
- [ ] **期望结果可验证**：不含模糊词（正确展示、功能正常、没有异常）
- [ ] **优先级合理**：P0 占比 30%~40%，P2 不超过 20%；场景测试用例默认为 P0
- [ ] **数据隔离覆盖**：权限测试至少覆盖两个不同主体的数据隔离
- [ ] **跨模块影响矩阵已完成**：已识别所有涉及本功能的关联模块，矩阵中的每个关联模块至少对应 1 条测试用例
- [ ] **跨模块数据一致性**：关联模块的测试用例中包含了具体的数据校验点
- [ ] **涟漪用例已覆盖**：功能 A 的数据出口、行为出口、入口来源均已检查，相关模块的测试用例已输出
- [ ] **关联文档链接有效**：文档信息中引用的链接可点击跳转
- [ ] **遵循命名规范**：文件名和用例名称符合 §2 规范
- [ ] **遗漏模式已排查**：已对照 §8 的 5 种常见遗漏模式逐项检查，无遗漏（或遗漏项已补充用例）

## 8. 常见用例遗漏模式与防御清单

> 本章节来自实战缺陷复盘。每发现一批因用例遗漏导致的线上/测试缺陷，在此记录遗漏模式、根因和防御方法。

### 模式 1：边界值"零跨度"遗漏

| 项 | 说明 |
|----|------|
| **典型缺陷** | 时间范围筛选"单日查询"（开始=结束=同一天），因开始和结束时间戳完全相同时 SQL `BETWEEN` 行为异常，查询返回空 |
| **为什么会漏** | 等价类划分时把"零跨度"错误归入"有跨度"的有效等价类。用例只测了"不限时间"和"跨天查询"，以为覆盖了所有场景 |
| **防御方法** | 任何范围类参数（时间范围、数值区间、分页范围），**必须为"零跨度"单独设计一条用例**：开始=结束、min=max、第1页=最后一页 |

**检查清单：**
- [ ] 时间范围筛选：是否包含"开始日期 = 结束日期"（单日查询）？
- [ ] 数值区间筛选：是否包含"最小值 = 最大值"（精确匹配一条）？
- [ ] 分页边界：是否包含"总数据量恰好 = 每页条数"和"总数据量 = 1"？

### 模式 2：对象生命周期"中间态"遗漏

| 项 | 说明 |
|----|------|
| **典型缺陷** | 创建对象"仅保存"（草稿态），相关展示字段为空；状态变更时操作类型记录错误；数据更改后变更详情完全不展示 |
| **为什么会漏** | 用例设计以"业务成功路径的终态"为默认视角，假设对象创建后所有字段已完整、操作类型判定永远正确、快照采集永远成功。没有穷举对象的生命周期状态 |
| **防御方法** | 对每个业务对象画出生命周期状态图，**为每个状态节点单独设计验证用例**。特别关注：草稿态（字段可能为空）、中间态（审核中/处理中）、异常态（采集失败/超时） |

**检查清单：**
- [ ] 业务对象的生命周期状态是否已完整列出（草稿 → 提交 → 审核 → 生效 → 归档/删除）？
- [ ] 是否覆盖了对象在"草稿态"（字段可能未分配）时的日志/展示行为？
- [ ] 是否覆盖了操作类型在非典型模块下的判定准确性？
- [ ] 是否覆盖了变更快照/详情采集失败时的降级展示（而非假设永远成功）？

### 模式 3：集成测试的"语法 vs 语义"陷阱

| 项 | 说明 |
|----|------|
| **典型缺陷** | 删除配置时，操作日志的模块路径错误记录。用例只验证了"路径格式正确（如 A > B）"，但格式正确 ≠ 内容正确 |
| **为什么会漏** | 集成测试的断言停留在**语法层面**（"看起来像路径格式"），没有做**语义层面**的精确匹配（"这条路径的期望值到底是什么"） |
| **防御方法** | 对于任何**有固定枚举值集合**的字段（操作模块路径、操作类型标签、状态名称等），集成测试断言必须**逐项写死期望值**，禁止使用"格式正确""非空""合理"等模糊断言 |

**检查清单：**
- [ ] 所有枚举类字段（模块路径、类型标签、状态名等）的期望结果是否写死了精确值？
- [ ] 是否对历史出过错的路径做了重点标注（在期望结果中加粗标出"绝非 XXX"）？
- [ ] 集成测试是否覆盖了"跨模块不串号"的验证（确认操作 A 的记录不会出现在模块 B 下）？

### 模式 4："正向推导"单向思维

| 项 | 说明 |
|----|------|
| **典型缺陷** | 多个模块缺少记录/埋点——用例只覆盖了 PRD 明确列出的模块，但 PRD 和实际代码覆盖范围不一致，导致部分模块漏覆盖 |
| **为什么会漏** | 用例设计从 PRD 文档出发做"正向推导"（PRD 说了什么 → 测什么），没有从代码/系统实际结构出发做"反向穷举"（系统有哪些模块 → 每个模块应该覆盖吗？） |
| **防御方法** | 在完成 PRD 正向推导后，**必须做一次反向穷举**：列出系统中所有可操作的模块/菜单，逐一标注"是否需覆盖"，对 PRD 未提及但实际存在操作的模块主动确认 |

**检查清单：**
- [ ] 是否从系统菜单树/路由表出发，反向穷举了所有可能产生操作的模块？
- [ ] PRD 中未明确提及的模块，是否主动与产品/开发确认了是否需要覆盖？
- [ ] 是否存在"PRD 说 A 模块有覆盖"但实际代码中 A 模块的某个子操作漏了？

### 模式 5：断言粒度过粗

| 项 | 说明 |
|----|------|
| **典型缺陷** | 模块路径展示为"X > A"应为"X > B"——这些错误在"格式正确"的断言下全部通过 |
| **为什么会漏** | 断言只校验字段**类型/格式**（非空、路径格式、标签颜色），不校验字段**值**（具体路径字符串、具体标签文字） |
| **防御方法** | 对关键业务字段，断言分为两层：① 格式校验（类型正确、非空）；② **值校验（精确字符串匹配）**。值校验必须逐条写死期望值，不可泛化 |

**检查清单：**
- [ ] 每个用例的期望结果，是否同时包含了"格式校验"和"值校验"？
- [ ] 对于路径类字段，是否写死了完整的期望路径字符串？
- [ ] 审核清单 §7 中的"期望结果可验证"是否已覆盖"值可验证"而不只是"格式可验证"？
